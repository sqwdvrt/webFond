# Фонд «Быть Добру»

Публичный сайт благотворительного фонда. Проект использует Next.js App Router,
TypeScript, Tailwind CSS, PostgreSQL и Prisma.

Правила и этапы находятся в [`PROJECT_PLAN.md`](./PROJECT_PLAN.md), краткий журнал
работы — в [`WORK_REPORT.md`](./WORK_REPORT.md).

## Требования

- Node.js 20.9 или новее;
- npm;
- PostgreSQL для работы с данными.

## Локальный запуск

```bash
npm install
cp .env.example .env
npx prisma migrate deploy
npm run db:generate
npm run dev
```

После запуска сайт доступен по адресу [http://localhost:3000](http://localhost:3000).

Перед первым запуском укажите рабочий `DATABASE_URL`. Команда
`prisma migrate deploy` применит начальную миграцию из `prisma/migrations`.

## Административная часть

Форма входа доступна по адресу
[http://localhost:3000/admin/login](http://localhost:3000/admin/login). Для нее
нужны серверные переменные:

```dotenv
ADMIN_USERNAME=""
ADMIN_PASSWORD=""
AUTH_SECRET=""
ADMIN_TRUST_PROXY="false"
```

Заполните логин и пароль вручную, а случайный секрет длиной не менее 32 символов
можно получить командой `openssl rand -hex 32`. Пустые значения из
`.env.example` намеренно не проходят проверку конфигурации.

`ADMIN_TRUST_PROXY=true` допустим только за reverse proxy, который перезаписывает
клиентские forwarding-заголовки. Рабочие значения хранятся в `.env` и не
добавляются в git.

После входа `/admin` открывает единую административную часть с обзором и
разделами обращений, проектов, новостей, документов, реквизитов и пожертвований.
Обзор получает счетчики, предупреждения и последние административные действия
через один серверный read model; клиентские компоненты не запрашивают эти данные
отдельно. Для
проектов, новостей, документов и реквизитов используются статусы `DRAFT`,
`PUBLISHED` и `ARCHIVED`; на публичных страницах показывается только контент со
статусом `PUBLISHED`.

Очередь `/admin/messages` ищет по имени, email и тексту обращения, фильтрует по
статусу и московским календарным датам и показывает по 25 записей на страницу.
Детальная карточка поддерживает `NEW`, `IN_PROGRESS`, `CLOSED` и `SPAM`, а также
приватную внутреннюю заметку. Сохранение защищено optimistic concurrency по
`updatedAt`: если запись уже изменена, форма просит обновить страницу вместо
перезаписи чужих изменений. Число новых обращений загружается в защищенном
server layout и передается в меню только как агрегированное число — отдельного
клиентского API для бейджа нет.

Изменения статусов/заметок обращений и жизненного цикла проектов, новостей и
документов записываются атомарно в `AdminAuditEvent`. Журнал хранит только тип
действия, тип и идентификатор сущности, безопасные прежний/новый статусы и время.
Имена, email, тексты обращений, внутренние заметки, содержимое публикаций и
секреты в audit log не сохраняются. Публичная отправка контактной формы audit
событие не создает.

Метрики пожертвований «сегодня» и «текущий месяц» используют успешные платежи и
`paidAt` в полуоткрытых интервалах `[start, end)` часового пояса
`Europe/Moscow`. Предупреждения считаются для новых обращений строго старше
48 часов, ожидающих пожертвований строго старше часа и безопасных кодов
readiness. Ровно 48 часов и ровно один час просрочкой не считаются.

Изображения проектов и новостей, а также документы можно задавать URL или
загружать через админку. Новые загруженные фотографии JPEG/PNG/WebP проверяются,
уменьшаются до 1440×1440 без увеличения и обрезки и сохраняются в WebP без EXIF.
Повреждённые, анимированные изображения и файлы с более чем 25 миллионами
пикселей отклоняются. Один процесс декодирует не более двух фото одновременно;
лишняя загрузка получает 503 с `Retry-After: 1`, без очереди в памяти.
Документы при загрузке принимаются только в PDF;
документы по внешнему URL не конвертируются и их формат не гарантируется.

В `/admin/donations` фильтры по статусу, дате создания и строке поиска
выполняются на сервере. CSV содержит только текущую отфильтрованную выборку и не
зависит от номера страницы. Календарные границы и отображение дат используют
`Europe/Moscow`.

Перед запуском новой версии примените миграции:

```bash
npx prisma migrate deploy
```

Команда применяет миграции к базе из `DATABASE_URL`, поэтому перед запуском
проверьте адрес и имя целевой базы. Миграция публикации сохраняет существующие
записи, заполняет статусы документов и даты уже опубликованных проектов и
новостей.

### Admin operations: эксплуатация

#### Deploy и pg_trgm

Миграция admin operations добавляет `SPAM`, `internalNote`,
`AdminAuditEvent`, `pg_trgm` и индексы очереди/поиска/метрик. Обычное создание
индексов на существующих `ContactRequest` и `Donation` блокирует запись, поэтому
production rollout выполняйте в согласованное окно обслуживания. Новый составной
индекс обращений создается до удаления старого. Перед deploy сделайте резервную
копию и проверьте наличие прав на `CREATE EXTENSION pg_trgm`. Если `pg_trgm` уже
установлен не в `public`, роль deploy также должна владеть расширением: миграция
переместит его в `public` до создания schema-qualified GIN-индексов и завершится
до application DDL, если прав недостаточно.

Интеграционную проверку этой миграции можно отдельно запустить на локальной
тестовой базе с установленным `psql`:

```bash
CONTENT_MIGRATION_TEST_DATABASE_URL="postgresql://localhost/foundation_test" \
  npm test -- src/db/content-migration.integration.test.ts
```

Защитная проверка принимает только `localhost` или `127.0.0.1` и имя базы с
суффиксом `_test`. Тест работает во временной изолированной схеме и удаляет ее
после завершения.

#### Локальная DB-проверка

Миграцию и прикладные admin operations можно проверить одной безопасной
локальной базой:

```bash
ADMIN_OPERATIONS_TEST_DATABASE_URL="postgresql://localhost/foundation_test" \
  npm test -- src/db/admin-operations-migration.integration.test.ts
ADMIN_OPERATIONS_TEST_DATABASE_URL="postgresql://localhost/foundation_test" \
  npm test -- src/features/admin-operations.integration.test.ts
```

Для обеих команд защитная проверка принимает только `localhost` или `127.0.0.1`
и имя базы с суффиксом `_test`.

Прикладной suite применяет все миграции в случайной схеме и проверяет реальные
репозитории: поиск/пагинацию обращений, московские границы пожертвований,
строгие alert cutoff, atomic audit/rollback и отсутствие audit у публичной формы.
Без переменной suite пропускается; это означает «не проверено на PostgreSQL», а
не успешный DB-прогон.

#### Откат

Для предупреждений используются точные строгие условия: `NEW` считается
просроченным только при `createdAt < now - 48 hours`, а `PENDING` — только при
`createdAt < now - 1 hour`. Равенство порогу не включает запись в предупреждение.

При проблеме после deploy предпочтителен forward-fix. Если всё же нужен откат
приложения, заранее подготовленная совместимая сборка может не показывать новые
поля в UI, но обязана использовать перегенерированный Prisma Client и Prisma
schema со значением enum `SPAM`. Исходный артефакт до миграции небезопасен и
запрещён, как только `SPAM` мог быть записан: неизвестное значение Prisma enum
может привести к ошибке декодирования строки.

Если совместимой сборки нет, аварийный путь требует резервную копию и
согласованное окно обслуживания: остановите запись, явно подсчитайте количество
строк `SPAM`, затем выполните одобренную транзакцию `SPAM → IN_PROGRESS` и
проверьте нулевой остаток `SPAM`. Это lossy-операция с потерей классификации;
оператор обязан записать исходный count, обоснование и результат в журнал
изменений. По умолчанию используется `IN_PROGRESS`, чтобы не закрывать обращения
молча. Аварийный remap должен успешно завершиться и провериться до запуска
старого артефакта.

Для PostgreSQL enum-значение нельзя удалить простой безопасной командой
`DROP VALUE`. Его удаление требует создания заменяющего enum-типа и
переписывания зависимых данных. Такая замена и переписывание требуют блокировок
и неприемлемы для аварийного отката.

Автоматический destructive down/откат схемы не предоставляется: добавленная
аддитивная схема остаётся на месте. Последующая очистка допустима только после
свежей резервной копии и доказательства, что число `SPAM` равно нулю, а
`internalNote` и audit больше не используются и от них ничего не зависит. Такая
очистка выполняется отдельной проверенной миграцией в новое окно обслуживания,
a не разовым ad-hoc SQL.

### Безопасность admin-маршрутов

Query-параметр поиска может содержать email и остается в истории браузера. В
production access-логи reverse proxy и хостинга должны удалять или не записывать
query string для маршрутов `/admin`.

Production-ответы `/admin` получают `Cache-Control: private, no-store,
max-age=0`. В режиме `next dev` Next.js может заменить его на `no-cache,
must-revalidate`; проверять итоговый заголовок нужно через `next build` и
`next start`.

### Папки писем и журнал изменений

В `/admin/messages` доступны «Входящие», «Архив» и «Корзина» независимо от
рабочего статуса обращения. На текущей странице можно выбрать до 25 писем и
переместить их в архив, корзину или вернуть во входящие. Удаление из списка
обратимо: физическое удаление и очистка корзины не предусмотрены. Статус и
внутренняя заметка сохраняются. Составные операции атомарны и проверяют
`updatedAt` и исходную папку; конфликт одного письма отменяет всю группу.

В обзоре выводятся пять последних действий. Полный журнал `/admin/changes`
показывает по 25 событий на страницу с датой по Москве, идентификатором и
ссылкой на существующий объект. В аудит папок записываются только ID и
прежняя/новая папка, без текста письма, имени и email.

Перед запуском этой версии примените `prisma migrate deploy`: миграция
`20261019100000_contact_folders` добавляет папку со значением `INBOX` для
существующих писем и новый тип события аудита. Миграция аддитивна, но во время
построения индекса на большой таблице требуется учитывать блокировку записи.
Старую версию с прежним Prisma Client нельзя использовать для чтения нового
значения enum в журнале без проверки совместимости; используйте forward-fix.

## Проверки

GitHub Actions запускает `quality` и `payments-integration` на pull request и
push в `master`/`develop`, на Node.js 22 и PostgreSQL 16. В workflow заданы
отдельные тестовые БД на `localhost` и оба Prisma URL. Общая проверка
`npm run verify` выполняется без опциональных DB-suite переменных; затем каждый
DB-suite запускается отдельным последовательным шагом со своей переменной.
Это обязательно: тест admin-миграции перемещает `pg_trgm`, общий для всей БД,
поэтому разные схемы не защищают от параллельного выполнения таких тестов.
Платежные интеграции выполняются отдельным job с собственным PostgreSQL.

Production-only `npm audit` обязателен в CI. Текущее dev-only предупреждение
`braces` и порядок его повторной проверки описаны в
[`docs/security/dependency-audit.md`](./docs/security/dependency-audit.md).

Перед запуском создайте `.env` и задайте обе переменные подключения:
`DATABASE_URL` и `DATABASE_URL_UNPOOLED`.

```bash
npm run verify
```

Команда запускает модульные тесты, линтер, проверку типов и схемы Prisma и сборку.
Проверка типов сначала генерирует игнорируемые декларации Next.js.
Это local working-tree pre-commit gate: staged и unstaged слои проверяются отдельно
на пробельные ошибки. Команда не является clean-checkout CI range gate.
DB-backed интеграционные проверки остаются отдельными командами, потому что им
нужна безопасная локальная тестовая база:

- платежи — `npm run test:integration:payments`;
- миграция контента — `npm test -- src/db/content-migration.integration.test.ts`.

## Платежи

Контур разового пожертвования через СБП реализован, но по умолчанию выключен.
`PAYMENTS_ENABLED=false`, пока нет утверждённой оферты и тестовых ключей ЮKassa.
Секрет ЮKassa используется только на сервере и не должен иметь префикс
`NEXT_PUBLIC_`.

Нужные серверные переменные:

```dotenv
PAYMENTS_ENABLED=false
PAYMENTS_OFFER_VERSION=
PAYMENTS_RATE_LIMIT_SECRET=
PAYMENTS_RECONCILE_SECRET=
PAYMENTS_TRUST_PROXY=false
YOOKASSA_SHOP_ID=""
YOOKASSA_SECRET_KEY=""
YOOKASSA_RETURN_URL="http://localhost:3000/donation/result"
```

`PAYMENTS_ENABLED=true` включает `/help` и `POST /api/payments/create` только если
оферта опубликована и `PAYMENTS_OFFER_VERSION` совпадает с её версией. Текущая
версия оферты: `2026-09-04`. Production требует HTTPS и `PAYMENTS_TRUST_PROXY=true`
за reverse proxy, который сам формирует forwarding-заголовки.

Маршруты:

- `POST /api/payments/create` — создание разового платежа СБП;
- `POST /api/payments/webhook` — уведомления ЮKassa `payment.succeeded` и
  `payment.canceled`;
- `POST /api/maintenance/payments/reconcile` — защищённая сверка зависших
  платежей по текущему статусу в ЮKassa;
- `/donation/result` — проверка результата, страница не индексируется.

Webhook не доверяет телу уведомления: сервер запрашивает платёж в ЮKassa и только
после этого меняет статус. Подписок и автосписаний нет.

После изменения схемы:

```bash
npx prisma migrate deploy
```

Проверки платежного контура:

```bash
npm test
PAYMENTS_TEST_DATABASE_URL="postgresql://postgres:postgres@localhost:5432/foundation_payments_test" \
  npm run test:integration:payments
```

Интеграционная команда обязательна: без безопасного URL тестовой базы она
завершается ошибкой, а не skip. Имя базы должно оканчиваться на `_test`.

До тестового магазина ЮKassa внешний QR, возврат на сайт и доставка webhook
проверяются детерминированными тестами с подменённым HTTP. Живой тестовый платёж
остаётся в этапе 5.

## Timeweb

Боевой сайт работает в Timeweb Cloud App Platform в Москве (`fond-bit-dobru.ru`).
Политика персональных данных не допускает иностранный хостинг, поэтому Vercel
и Neon не являются production.

В панели приложения:

- framework: Next.js (не Nest);
- Build: `npm run timeweb-build` — `prisma generate`, `prisma migrate deploy`,
  затем `next build`. `DATABASE_URL` должен быть доступен на сборке;
- Run: `npm run timeweb-start` — только `next start` на `0.0.0.0` и `$PORT`.
  Миграции не должны выполняться при каждом рестарте процесса;
- `GET /api/health` — platform liveness (ответ `{ "ok": true }`, без авторизации);
- Post-deploy configuration readiness: `GET /api/ready` проверяет конфигурацию
  административного доступа и отвечает `503`, если она некорректна;
- `NEXT_PUBLIC_SITE_URL=https://fond-bit-dobru.ru` задаётся **до сборки**:
  Next.js вшивает `NEXT_PUBLIC_*` на build. `SITE_URL` — тот же origin на
  рантайме.

`next/image` на этом хосте идёт без серверного оптимизатора: рантайм не может
писать в `/app/.next/cache/images`.

Новые фото оптимизируются Sharp в памяти перед отправкой в объектное хранилище;
запись в `cache/images` для этого не нужна. Существующие URL и банковские QR
не преобразуются. UUID-объекты в S3 получают годовой immutable Cache-Control;
файл с изменённым содержимым всегда загружается по новому URL. Знак шапки
104×104 создаётся из оригинала командой `node scripts/prepare-brand-images.mjs`.

### Очистка технических счётчиков

Очистка rate-limit buckets работает независимо от онлайн-платежей:
`POST /api/maintenance/rate-limits/cleanup`, без тела и query string,
с заголовком `x-maintenance-secret`. В runtime задайте отдельный
`MAINTENANCE_SECRET` — случайный ASCII-секрет длиной не менее 32 символов;
не передавайте его в URL или логи.

Для scheduler Timeweb используйте запуск раз в минуту:

```bash
node scripts/run-rate-limit-cleanup.mjs
```

Задача получает `SITE_URL` и `MAINTENANCE_SECRET` из окружения, делает один
HTTP-запрос с timeout и печатает только время/количество удалённых строк.
Если scheduler поддерживает только HTTP, настройте тот же POST и заголовок
в его защищённых настройках, оставив тело пустым. Проверяйте код завершения,
свежесть успешного запуска и ошибки в журнале scheduler.

Каждый запуск удаляет не более 1000 просроченных строк. `batchFull=true`
означает полный пакет, а не точную гарантию следующей строки; при постоянно
полных пакетах проверьте рост backlog и частоту запусков. Активные счётчики
не удаляются, параллельные задачи используют `SKIP LOCKED`; SQL ограничен
двумя секундами. При отсутствии настройки endpoint отвечает 503, неверном
секрете — 401; секреты и ключи счётчиков в ответ не попадают.

До подтверждения как минимум двух успешных запусков production scheduler
сохранена прежняя очистка при создании платежа. Удалять её из горячего пути
следует отдельным изменением после активации scheduler. Наличие endpoint
в коде само по себе не означает, что production-расписание уже настроено.

### Воспроизводимые измерения

Нагрузочные фикстуры допускаются только в локальной БД
`foundation_optimization_test`; рабочая БД для них запрещена. Примените миграции
к этой тестовой БД, задав оба Prisma URL. Затем:

```bash
PERF_SEED_DATABASE_URL="postgresql://localhost/foundation_optimization_test" node scripts/performance-seed.mjs
PERF_SEED_DATABASE_URL="postgresql://localhost/foundation_optimization_test" npx vitest run --config vitest.performance.config.ts
PERF_BASE_URL="http://127.0.0.1:3317" PERF_CONCURRENCY=1 node scripts/measure-public-performance.mjs
PERF_BASE_URL="http://127.0.0.1:3317" PERF_CONCURRENCY=5 node scripts/measure-public-performance.mjs
```

HTTP-замеры требуют запущенную production-сборку на этом локальном origin.
Каждый маршрут прогревается, затем выполняются три серии по 100 запросов;
измеряются p50/p95 TTFB, размер тела и ошибки. Опциональный `PERF_SERVER_PID`
добавляет снимок RSS процесса; это не измерение пиковой памяти.
`node scripts/performance-seed.mjs --clean` с тем же URL удаляет только
собственные `perf-*` фикстуры. Read-model harness не входит в обычный unit-прогон.

### Диагностика health и readiness

В Timeweb используйте `/api/health` для platform liveness. `/api/ready` —
отдельная post-deploy проверка конфигурации, а не проверка PostgreSQL.
При `503` проверьте переменные окружения запущенного приложения:

- `ADMIN_USERNAME` и `ADMIN_PASSWORD` не должны быть пустыми;
- `AUTH_SECRET` после удаления пробелов по краям должен содержать не менее 32 символов;
- `ADMIN_TRUST_PROXY` должен быть явно задан как `true` или `false`:
  локально без reverse proxy — `false`, в Timeweb за доверенным proxy — `true`.

После изменения окружения перезапустите приложение и повторите оба запроса.
Не выводите секреты в логи. Ответ readiness намеренно содержит только
`{ "ok": false }` при некорректной конфигурации; не заменяйте `503` постоянным `200`.
Успешный readiness не подтверждает доступность базы, применение миграций или
работоспособность платежей.

Базу проверяйте отдельно: запросом `SELECT 1` и командой
`npx prisma migrate status` в окружении с настроенными `DATABASE_URL` и
`DATABASE_URL_UNPOOLED`. Prisma CLI сам по себе не загружает `.env.local` Next.js:
используйте окружение приложения или заранее безопасно загрузите переменные.
`migrate status` не применяет миграции; ненулевой код требует проверки результата,
в частности наличия ожидающих или неуспешных миграций.
Миграции выпуска применяются существующей командой сборки `timeweb-build`,
а не диагностикой и не при каждом рестарте.

Перед выпуском в панели Timeweb отдельно подтвердите путь liveness, runtime
переменные, доступность production PostgreSQL и статус миграций. Публичные
ответы endpoint не позволяют проверить настройки панели или историю миграций.

Загрузки в production идут в объектное хранилище Timeweb S3, не в `public/` и
не в Vercel Blob. Локальный диск контейнера недолговечен и часто только для
чтения.

### Админка: улучшенный рабочий процесс

В списках проектов, новостей и документов доступны поиск, статус, сортировка и
серверные страницы по 25 записей. Параметры списка сохраняются при переходе в
редактор и после сохранения. Проекты и новости имеют предпросмотр текущих полей;
действия черновика, публикации и архива различаются. Формы предупреждают о потере
несохранённых правок при закрытии вкладки и переходе по ссылке. Переходы
«назад/вперёд» внутри SPA не блокируются через недокументированные API роутера.

Загрузки показывают превью/метаданные, блокируют сохранение на время запроса и
игнорируют ответ устаревшей загрузки. Очистка ссылки не удаляет файл из хранилища.
Изменения реквизитов, сохранение контента и ручные проверки отражаются в аудите;
журнал содержит названия изменённых полей без их значений. Доступ к админке общий,
поэтому журнал не определяет персонального сотрудника.

Для выпуска требуется миграция `20261019090000_admin_workflow_audit` перед запуском
нового приложения. Применяйте её штатной командой `timeweb-build`. При откате кода
оставьте новые enum и колонку `changedFields` в БД: откат данных не требуется.

Сверка выбирает подходящие платежи до ограничения пачки. Автоматическая политика:
не раньше 5 минут после создания, до 8 попыток, возраст до 90 дней, ограничение
работы пачки 20 секунд с отдельным таймаутом каждого запроса. Исчерпавшие лимит
записи помечаются для ручного разбора и не блокируют следующие платежи. Ручная
проверка выбранной записи допускает более старый платёж, получает lease атомарно
и сбрасывает лимит попыток. Терминальные статусы не перезаписываются.

`POST /api/admin/payments/reconcile` требует административную сессию:

- `{ "mode": "batch", "limit": 25 }` — готовая к проверке пачка;
- `{ "mode": "single", "donationId": "<local-donation-id>" }` — выбранная запись;
- старое тело `{ "limit": 25 }` также поддерживается.

Лимит ручного запуска — 20 команд за минуту; превышение возвращает `429` с
`Retry-After`. Гость получает `401`, неверное тело — `400`, занятая запись — `409`,
отсутствующая запись — `404`, запись без provider ID — `422`. Ответ не содержит
email или полного ответа ЮKassa. CSV сохраняет прежний набор колонок; фильтры
диагностики не меняют формат экспорта.

Настройте scheduler на `POST /api/maintenance/payments/reconcile` каждые 5 минут,
с заголовком `x-reconcile-secret` и телом `{ "limit": 25 }`. После успешного job
обновляется `SiteSetting.paymentsReconciliationHeartbeat`; при включённых платежах
обзор предупреждает об отсутствии проверки более 15 минут и ошибках последнего
job. Код endpoint и документация не создают расписание на платформе автоматически.

### Совместимость способов оплаты и восстановление зависших статусов

`payment_method` в ответе ЮKassa необязателен. Его отсутствие или новый строковый
тип не блокируют сверку. Это не включает дополнительные способы оплаты в магазине:
ими по-прежнему управляют настройки ЮKassa. Статус подтверждается авторизованным
GET по ID платежа, совпадением ID, `metadata.donationId`, суммы и валюты.
Для `succeeded` дополнительно обязательны `paid: true` и корректный `captured_at`.
Некорректная структура ответа, конфликт ID или терминальных статусов не игнорируются.

После деплоя исправления отфильтруйте в админке платежи с ручной проверкой и кодом
`payment_method_mismatch`. Запустите проверку каждой такой записи: старые ручные
отказы намеренно не возвращаются в автоматическую очередь без действия оператора.
Проверка повторно читает API ЮKassa, снимает флаг ручного разбора после успешной
сверки и не перезаписывает терминальные статусы. Не выставляйте успех напрямую
в базе по скриншоту, email или сумме.

Неуспешные API-проверки выводят `payment_reconciliation_failed`: ID платежа,
ID пожертвования, статус провайдера, тип способа оплаты (или `null`), результат
и код причины. Нестандартные и слишком длинные значения скрываются. Полный ответ,
email, данные карты и секретные ключи в эту диагностику не попадают.

Для проверки scheduler сверяйте свежесть `paymentsReconciliationHeartbeat` и
предупреждение на обзоре админки. Если heartbeat отсутствует или устарел, сначала
проверьте расписание, заголовок `x-reconcile-secret` и результат выполнения job
в Timeweb. Не публикуйте значение секрета и не передавайте его в URL.

Интеграционные тесты очереди запускаются вместе с `npm run test:integration:payments`
на отдельной локальной PostgreSQL с безопасным `PAYMENTS_TEST_DATABASE_URL`.

## Vercel

Vercel — только превью без боевого домена и без персональных данных.
Сборка выполняет `prisma generate`, затем `prisma migrate deploy`, затем
`next build` (`npm run vercel-build`). Не направляйте `fond-bit-dobru.ru` на
Vercel и не подключайте preview к боевой базе Timeweb.

Если превью всё же поднимают, задайте `ADMIN_TRUST_PROXY=true`,
`PAYMENTS_TRUST_PROXY=true` и `PAYMENTS_ENABLED=false`. `DATABASE_URL` для
такого превью — отдельная база, не кластер production. `DATABASE_URL_UNPOOLED`
нужен `prisma migrate deploy` на этой отдельной базе.

Локальная копия переменных панели может лежать в gitignored-файле
`.env.vercel.local`.

## Ограничения контента

Новости, отчеты, банковские реквизиты и юридические тексты не публикуются до
проверки. Публичные страницы читают только записи со статусом `PUBLISHED`.
Загруженные через админку документы проверяются как PDF, фотографии
нормализуются перед сохранением. Для документов, заданных внешними ссылками,
конкретный формат не гарантируется.
