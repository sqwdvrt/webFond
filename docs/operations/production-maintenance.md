# Production: включение очистки и откат

Состояние на 19 октября 2026: endpoint и runner опубликованы в master;
production-секрет и расписание ещё не заданы, два production-запуска не подтверждены.
Старая очистка в платежном запросе сохранена до подтверждения нового расписания.

## Действия владельца

1. В Timeweb: App Platform → Cute Callisto (ID 245187) → Настройки →
   Настройки деплоя / Редактировать → Переменные → Добавить.
2. Создать отдельный секрет локально командой `openssl rand -hex 32`.
   Добавить его как `MAINTENANCE_SECRET` и сохранить в менеджере паролей.
   Не отправлять значение в чат, Git или URL. Ввод нового credential в панели
   выполняет владелец. `SITE_URL` должен быть `https://fond-bit-dobru.ru`.
3. Сохранить настройки, выполнить деплой актуального master и дождаться успеха.
4. Предоставить существующий постоянный сервер с Node.js 22+ и cron
   для расписания либо подтвердить доступный защищённый HTTP-планировщик.
   В осмотренных настройках App Platform встроенного scheduler не обнаружено.
   Не устанавливать cron внутри временного контейнера приложения:
   он может пропасть при следующем деплое.

## Точное задание для существующего Linux-сервера

Скопировать `scripts/run-rate-limit-cleanup.mjs` в
`/opt/webfond-maintenance/run-rate-limit-cleanup.mjs`.
Создать `/etc/webfond-maintenance.env`, доступный только владельцу задания
(`chmod 600`), со строками:

```sh
SITE_URL=https://fond-bit-dobru.ru
MAINTENANCE_SECRET=<тот же секрет, что в Timeweb>
```

Подставить реальный абсолютный путь к Node.js (`command -v node`).
Пример записи crontab для `/usr/bin/node`:

```cron
* * * * * /bin/sh -c 'set -a; . /etc/webfond-maintenance.env; set +a; exec /usr/bin/node /opt/webfond-maintenance/run-rate-limit-cleanup.mjs' >> /var/log/webfond-maintenance.log 2>&1
```

Журнал и файлы принадлежат пользователю задания; обеспечить ему права записи
и ротацию журнала. Секрет не включать в командную строку cron.
Проверить два последовательных запуска по расписанию с интервалом около минуты:
код завершения 0 и `event=rate_limit_cleanup_completed`, корректные
`completedAt`, `deleted` от 0 до 1000 и `batchFull` boolean.
Ноль удалённых строк — нормальный успешный результат.
Ошибки означают неготовность к отключению старой очистки.
После двух успешных запусков передать только строки результата без секретов:
затем отдельным коммитом удалить старый вызов cleanup из платежного запроса,
проверить платежные тесты и выпустить обновление.

Для HTTP-планировщика: POST
`https://fond-bit-dobru.ru/api/maintenance/rate-limits/cleanup`,
каждую минуту, пустое тело, защищённый заголовок `x-maintenance-secret`.
Ожидается HTTP 200 с `{deleted, batchFull}`. Не использовать GitHub Actions
для минутного расписания: это не гарантированный минутный scheduler.

Оптимизация новых миграций не добавляет. После отката проверить `/api/health`,
админку, папки обращений, историю и отображение платежей.
