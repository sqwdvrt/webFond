# Выпуск исправлений аудита

## До выпуска

- Зафиксировать исходный и целевой commit SHA, успешный CI и production audit.
- Проверить резервную копию и подготовленный совместимый артефакт отката.
- Выполнить `npm ci`, `npm run verify`, PostgreSQL integration и `npm run test:e2e`
  на отдельной локальной/CI-базе `_test`. Пропуск suite не означает успех.
- Согласовать окно работ и заранее проверить возможность приостановки новых записей
  на общем reverse proxy/входе всех экземпляров приложения.
- Согласовать версии документов с владельцем; тексты в этом выпуске не меняются.

## Миграция согласий

Миграция `20261117193000_consent_evidence` добавляет nullable-поля согласия
ContactRequest/Donation и принятия оферты Donation. Исторические строки остаются
null — не создавать согласия задним числом.

1. На общем входе временно закрыть POST создания платежей и POST server action
   контактной формы; дождаться завершения уже принятых запросов. Не блокировать
   webhook, /donation/result и сверку ранее созданных платежей.
2. Применить `prisma migrate deploy` к проверенной целевой БД через штатный deploy.
3. Заменить все инстансы приложения и проверить версию каждого. Одной замены
   «главного» экземпляра при rolling deploy недостаточно.
4. Проверить evidence на контрольных записях и отсутствие ошибок миграции.
5. Открыть новые записи и записать T0. Все записи после T0 должны иметь evidence.
   Записи, завершённые до остановки старых инстансов, относятся к прежней версии.

Если общий запрет POST недоступен, не выпускать rolling update без отдельного
проверенного промежуточного совместимого релиза. `PAYMENTS_ENABLED=false` не
останавливает контактную форму.

## После выпуска

- Проверить /, /help, /contacts, /requisites, /api/health, /api/ready.
- Проверить GET /api/maintenance/status с `x-maintenance-secret`; секрет не в URL.
- Убедиться, что гость перенаправляется из /admin к форме входа.
- Проверить согласия, QR, scheduler и существующие платежи; провести приёмку по
  отдельному журналу. HTTP 200 health/ready не доказывает доставку чека.

## Откат

Предпочтителен forward-fix. Аддитивные колонки оставлять, down SQL не выполнять.
Старая версия не пишет evidence: перед откатом остановить новые записи и держать
их закрытыми до возвращения совместимого кода. Webhook/сверка должны использовать
версию, совместимую со всеми enum текущей БД. Повторная попытка существующего
платежа не должна заменять его исторические версии согласий.
