# План уточнения удобства публичного сайта

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Завершить шесть пользовательских замечаний с учётом уже внесённых исправлений, не повторяя работу и не публикуя неподтверждённые обещания фонда.

**Architecture:** Доработать существующие страницы, BankQrTransfer и формы. Разделять общие реквизиты фонда и выбранный банковский счёт, использовать одинаковые тексты подсказок в связанных местах. Новые таблицы, API, CRM и редактор условий помощи в админке для этого этапа не нужны.

**Tech Stack:** Next.js/React/TypeScript, существующие Vitest/Testing Library/axe и Chromium smoke-тесты; ручная проверка VoiceOver и банковских приложений.

Дата анализа: 18 ноября 2026. Основание — исходный аудит и фактический код коммита
`2ef6806`. Этот документ — план следующих уточнений; новые изменения приложения
и повторная проверка production в рамках составления плана не выполнялись.
Ранее выполненные тесты относятся к 17 ноября, а не являются сегодняшним прогоном.

## Границы

- Наполнение проектами, новостями, отчётами и другими фактами о деятельности по-прежнему отложено.
- География, сроки ответа и часы связи ранее обозначены владельцем как «не определены». Повторно запрашивать эти сведения сейчас не требуется.
- Пуш предыдущего коммита подтверждён. Сам по себе пуш не подтверждает выкладку и работу новых сценариев на боевом домене.
- Платёжный контур и схема согласий уже изменены в предыдущем выпуске. Этот план не предполагает переписывать их заново.

## 2. Рекомендуемый способ выполнения

Три возможных подхода:

1. **Небольшие правки существующих блоков — рекомендуется.** Использовать текущий переключатель счетов, формы и тесты. Быстро проверить, минимальный риск для оплаты.
2. **Объединить всю страницу реквизитов вокруг одного переключателя.** Последовательнее визуально, но потребуется переработать взаимодействие опубликованных реквизитов из БД и статических счетов/QR. Для текущих замечаний это лишняя смена источников данных.
3. **Сделать инструкции и условия управляемыми из админки.** Удобно при частых обновлениях, но нужны модель, валидация, публикация, права и история. Пока условия не определены, усложнение не оправдано.

Последовательность: документация → понятность счетов/ссылок → согласованность
инструкций → доступность → проверка после публикации. Фактические условия помощи
подключить отдельным небольшим изменением, когда они появятся.

## 3. Задача A — условия помощи и ожидание ответа

**Сейчас:** /need-help просит краткое описание и город, обещает уточнить возможность
помощи; раздел «Когда ответим» не задаёт срок. /contacts показывает юридический
адрес и телефоны без часов. Посетитель не может понять, когда напомнить об обращении
и можно ли приезжать. Из этого нельзя делать вывод о режиме работы фонда.

**Файлы:** `src/app/need-help/page.tsx`, `src/app/contacts/page.tsx`, `src/content/faq.ts`;
тесты `src/app/need-help/page.test.tsx`, `src/app/information-pages.test.tsx`, `src/components/content/faq-list.test.tsx`.

### A1. Что можно уточнить без новых фактов

- [ ] Свести текущие обещания в таблицу: куда придёт ответ, какие сведения нужны, кто рассматривает возможность поддержки. Не добавлять неизвестный срок, географию и расписание.
- [ ] Подготовить короткую единообразную формулировку: «Укажите город или район и кратко опишите, какая поддержка нужна. Возможность помощи фонд уточнит при рассмотрении обращения».
- [ ] В ответах за близкого человека уточнить: для первого сообщения достаточно описать ситуацию без ФИО, документов и других персональных данных этого человека. Не запрещать само обращение за близкого.
- [ ] Согласовать FAQ с предупреждением формы: запрос дополнительных документов фондом не должен звучать как приглашение прислать их сразу через сайт.
- [ ] Не писать «приезжайте», «принимаем по записи», «позвоните в рабочее время», пока такой порядок не подтверждён.
- [ ] Не назначать произвольные «3 дня», «до 18:00» или «напомните через неделю». Формулировку о повторном обращении оставлять без вымышленного порога.

**Проверка:** страницы и FAQ не противоречат друг другу, не гарантируют помощь,
не требуют лишних данных. Редакторская проверка достаточна для текста; автоматические
тесты нужны на существенные обещания и сохранность маршрута к форме, не на каждую запятую.

### A2. Что отложено до определения условий

Подготовить для владельца одну внутреннюю карточку, без публичных заглушек:

| Сведение | Что потребуется решить |
|---|---|
| География | Какие территории реально обслуживаются, есть ли исключения |
| Ограничения | Какие виды запросов рассматриваются и какие не принимаются |
| Первый ответ | Ориентир первого контакта отдельно от решения по помощи; рабочие или календарные дни |
| Повторное обращение | Когда и каким способом напомнить, какие сведения указать для поиска обращения |
| Телефоны | Часы и часовой пояс, разные ли назначения у двух номеров |
| Адрес | Только юридический адрес или место приёма; разрешено ли публиковать порядок посещения |

После появления утверждённых значений обновить /need-help, /contacts и FAQ в одном
изменении. Если потребуется общее место хранения повторяющихся текстов — небольшой
`src/content/contact-guidance.ts`, а не таблица БД. До этого не создавать конфигурацию
из пустых полей ради будущего использования.

**Готово A:** нейтральный сценарий согласован. Фактические часы/география отмечены
как «ожидают определения», а не «реализованы».

## 4. Задача B — реквизиты, выбор счёта и полезный переход

**Наблюдение:** на /requisites общая таблица берёт счёт из опубликованных реквизитов
БД, а QR-переключатель использует четыре счета из `src/content/bank-qr.ts`. Это два
разных источника. При выборе, например, Т-Банка таблица общего счёта не меняется.
Текущая ссылка #bank-details ведёт к общей таблице, а не к выбранному счёту.
Данные могут быть корректны в обоих местах, но пользователь должен понимать,
какой набор он копирует. Это проблема ясности, а не установленная ошибка счета.

**Файлы:** `src/components/donation/bank-qr-transfer.tsx`,
`src/components/requisites/copy-button.tsx`, `src/app/requisites/page.tsx`,
`src/app/help/page.tsx`, `src/app/globals.css`,
тесты обоих компонентов и `tests/e2e/smoke.spec.ts`.

### B1. Ясно назвать два назначения

- [ ] Перед переключателем: «Выберите один из счетов фонда. Необязательно выбирать банк, в котором обслуживаетесь вы».
- [ ] После выбора показывать «Выбранный счёт фонда: [банк]»; QR, БИК, счёт и копирование берутся из одного selected-объекта.
- [ ] Для общей таблицы использовать заголовок «Общие реквизиты фонда» и отдельное название кнопки, например «Скопировать общие реквизиты».
- [ ] Кнопку выбранного счёта назвать «Скопировать счёт [банк]» либо «Скопировать реквизиты [банк]». Компоненту копирования добавить необязательный label; не менять другие вызовы без необходимости.
- [ ] Не менять номера счетов и изображения, не превращать статические счета в автоматически редактируемую копию реквизитов из БД.

### B2. Не терять выбранный счёт при переходе

- [ ] На /help оставить переход «Все реквизиты фонда» к /requisites. Он означает переход к общему разделу, а не перенос выбора банка.
- [ ] На /requisites вместо неоднозначной повторной ссылки использовать «К общим реквизитам фонда» → #bank-details. Выбранные реквизиты при этом остаются раскрытыми в своём блоке.
- [ ] Для ручного перевода из другого банка предложить копировать именно уже показанный выбранный счёт — без обязательного перехода на другую страницу.
- [ ] При переходе по якорю проверить положение под sticky-header и фокус: фокусируемая цель уже есть, нужно подтвердить поведение браузера и диктора.
- [ ] Если по итогам просмотра переход к общей таблице ничего не помогает пользователю, убрать ссылку на /requisites, сохранив выбранные данные. Не заменять её принудительной синхронизацией двух источников.

### B3. Короткая инструкция вместо смешения способов

Три шага обычного перевода: выбрать счёт фонда → открыть QR или скопировать реквизиты
→ сверить получателя и сумму в приложении банка. Сохранить видимое пояснение,
что это перевод по реквизитам, а онлайн-оплата через ЮKassa — отдельный способ.
Не обещать отсутствие комиссии или распознавание любого QR любым банковским приложением.

### B4. Проверки до и после изменения

- [ ] Написать регрессию: выбрать Т-Банк, затем ВТБ; проверить название, QR, БИК, счёт и содержимое clipboard для каждого выбора.
- [ ] Проверить подписи двух кнопок и отсутствие одинакового непонятного «Скопировать реквизиты» для разных наборов на одной странице.
- [ ] Проверить состояние без выбора; клавиши стрелок в radio-group; переход по якорю; копирование при отказе Clipboard API.
- [ ] Проверить 360/390/768/1440 px и масштаб 200%, длинное название банка, полный номер счёта, читабельность QR.
- [ ] Ручная проверка четырёх QR в реальных банковских приложениях: распознанный получатель/счёт совпадают с утверждёнными. Денежный перевод для этой проверки не нужен; неподтверждённый банк отметить отдельно.

**Команды:** `npx vitest run src/components/donation/bank-qr-transfer.test.tsx src/components/requisites/copy-button.test.tsx src/app/information-pages.test.tsx`;
browser smoke — по инструкции `tests/e2e/README.md` на отдельной локальной БД.

**Готово B:** каждый набор реквизитов имеет явное название, выбранный счёт не
подменяется общим в объяснении, переходы полезны, копирование проверено.

## 6. Задача D — доступность honeypot и ошибок

**Уже сделано:** обе ловушки «Сайт» скрыты от accessibility tree и исключены из Tab.
Их серверная обработка сохранена. Удалять поле или делать disabled нельзя — это
поменяет защиту формы, а не только её доступность.

**Файлы:** обе формы, существующие UI/axe-тесты; при обнаружении проблемы — только
затронутый компонент. Добавление новой инфраструктуры доступности не требуется.

- [ ] Пройти контактную и платёжную формы только Tab/Shift+Tab: ловушки нет в порядке, фокус виден, не возникает неожиданных остановок.
- [ ] Пройти VoiceOver + Safari: ловушка не озвучивается; имя/email/сообщение/согласия имеют понятные подписи; ссылки в согласиях доступны отдельно.
- [ ] Проверить VoiceOver для суммы/radio банка, ошибок согласия, неуспеха отправки и успешного состояния; фокус не должен оказаться в скрытой группе.
- [ ] Проверить ссылки aria-describedby имени/email: сейчас указатели заданы всегда, а элементы ошибок существуют условно. При необходимости формировать атрибут только при наличии соответствующего сообщения.
- [ ] Проверить, требуется ли переместить фокус к первому ошибочному полю после server action; внедрять это только при воспроизведённой потере ошибки/контекста, без произвольных focus-прыжков.
- [ ] Сохранить автоматические регрессии: queryByRole не видит «Сайт», DOM input присутствует, заполненный honeypot не создаёт запись.

**Готово D:** автоматические проверки плюс записанная ручная проверка диктором.
Если VoiceOver не проверен, этот пункт остаётся «не проверено вручную», даже при зелёном axe.

регрессия, затем минимальное исправление и проверка. Текстовые изменения проверять
редакторски, без тестов, зеркалящих каждую фразу. Один логически связный пакет —
один коммит. Не включать в них изменения схемы согласий/платёжного провайдера.

## 9. Проверка после публикации

- [ ] Подтвердить успешный deploy нужного commit; затем открыть production как посетитель.
- [ ] Пройти главная → помощь → QR → выбранный счёт → копирование → общие реквизиты.
- [ ] Пройти нужна помощь → форма: одинаковые инструкции, предупреждение видно, ловушки нет в AX/Tab.
- [ ] Проверить desktop/mobile, клавиатуру, возвраты и FAQ; подтвердить отсутствие перезагрузки страницы «ради той же страницы».
- [ ] Тестовое обращение отправлять только с разрешённым тестовым адресом; для текстовых/QR-правок новая реальная оплата не нужна.
- [ ] Записать устройство/браузер/версию релиза и результат каждой ручной проверки, не публикуя персональные данные.

**Итог:** закрывать исходные шесть пунктов по отдельности. Фактические условия помощи
остаются ожидающими данных; банковские приложения и скринридер — ожидающими ручной
проверки, пока нет результата. Наполнение сайта деятельностью в этот план не входит.
