# Итоги улучшения публичного сайта

Проверено 19 октября 2026 года, Europe/Moscow. Локальные изменения не развёрнуты на production.

## Выполнено по этапам

| Этап | Результат |
| --- | --- |
| 1. Readiness | Разделены проверки живости, admin-auth и БД; инструкция диагностики добавлена в README. Локально и на действующем сайте health/ready отвечают 200. Исторический 503 не воспроизводится. |
| 2. QR и CSS | QR используют next/image без преобразования PNG; оригиналы скачиваются. Удалён повтор CSS. |
| 3. Пожертвования | При выключенной оплате основной путь ведёт к банковскому переводу. Одно сообщение о недоступности онлайн-оплаты; при включённой оплате сохранены форма и выбор проекта. |
| 4. Мобильный интерфейс | Компактные hero и логотип, заметное обращение за помощью; модальное меню, блокировка фона, циклический Tab и возврат фокуса. |
| 5. Доверие | Выделены ОГРН/ИНН, ссылки на документы, цели пожертвований по оферте. Главная загружает до трёх проектов и документов; суммы используют общий расчёт, даты берутся из записей. Ошибки источников изолированы. |
| 6. Проверки | Полный verify и проверка локальной production-сборки прошли. Условия выпуска перечислены ниже. |

При итоговой проверке дополнительно исправлены два длинных тире в подсказках
административной формы, нарушавшие существующий тест текстов, и сброс статуса
«Скопировано» при смене банка. Последняя ошибка воспроизведена тестом до исправления;
после исправления тест проходит.

## Проверки

- `npm run verify`: код завершения 0. 1312 тестов пройдено, 12 пропущено,
  128 файлов тестов прошли, 4 пропущены. Пропуски интеграционных наборов не
  интерпретируются как успешное выполнение этих наборов.
- ESLint, TypeScript, Prisma validate, production build, staged/unstaged diff checks прошли.
- Для запуска verify из `.env.local` в окружение команды переданы только
  DATABASE_URL и DATABASE_URL_UNPOOLED. Остальные локальные настройки не подмешивались
  в unit-тесты. Next.js загружал свои настройки штатно при сборке.
- Локальный production-сервер проверен на порту 3100 с выключенными платежами,
  второй временный процесс на 3101 использован только для проверки доступной онлайн-формы.
  Флаг оплаты и версия оферты заданы только этим временным процессам.
  Оба процесса остановлены; `.env.local` и production-настройки не менялись.
- 17 маршрутов ответили 200: главная, about, help, need-help, projects, news,
  reports, requisites, contacts, privacy, personal-data-consent, donation-offer,
  cookies, robots.txt, sitemap.xml, api/health и api/ready.
- `/donation/result` без идентификатора пожертвования штатно возвращает 404;
  это соответствует проверке входных параметров, а не поломке страницы.
- Chromium: путь с главной к переводу и обращению за помощью, выбор обоих банков,
  копирование соответствующих счетов, скачивание PNG, меню и его клавиатурное
  управление, пустые состояния, онлайн-форма. Ошибок browser console/pageerror нет.
- SHA-256 скачанных QR совпали с оригиналами; имена файлов qr-alfa.png и qr-vtb.png.
  QR на скриншотах реально отрисованных изображений считываются программно;
  счет и ИНН совпадают с реквизитами для каждого банка.
- Ранее в этапе 4 проверены ширины 320, 375, 390, 768 и 1280 px и увеличение
  текста до 200%: горизонтальной прокрутки нет, обе основные мобильные кнопки
  видны без прокрутки при обычном масштабе.

Онлайн-форма проверялась без отправки платежа. Реальных списаний и публикации
тестовых финансовых сведений не выполнялось.

1. В панели Timeweb подтвердить liveness `/api/health`, runtime admin-auth/proxy
   настройки, подключение production-БД и статус миграций. Панель и production-БД
   в этой работе не инспектировались. Публичные health и ready действующего сайта
   возвращают 200, но не подтверждают состояние миграций и платёжной интеграции.
2. Перед production-миграциями сделать резервную копию и проверить комплект
   выпуска. Миграция admin_operations строит обычные индексы с блокировкой записей,
   поэтому для неё требуется окно обслуживания согласно её SQL-комментарию.
3. Опубликовать подтверждённые документы и проекты через существующую админку.
   Для наполненного состояния есть тесты с изолированными фикстурами; реальные
   отчёты, результаты и суммы не создавались вместо материалов фонда.
4. Проверить QR камерой и через импорт файла в банковских приложениях на реальном
   телефоне. Программное считывание не заменяет эту проверку.
5. Выполнить отдельный согласованный деплой в Timeweb штатной командой сборки
   `npm run timeweb-build`, затем проверить маршруты, health/ready, проекты/отчёты,
   обращение за помощью и актуальный способ пожертвования. Не включать платежи
   только ради проверки. При регрессии вернуть предыдущую версию приложения;
   откат схемы и восстановление БД требуют отдельного решения по совместимости.
