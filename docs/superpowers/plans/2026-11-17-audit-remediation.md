> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Устранить технические и пользовательские замечания аудита 17 ноября, сохранив работающий сайт и существующий платёжный контур.

**Architecture:** Несколько небольших выпусков: зависимости → согласия и формы → QR/доступность → мониторинг и обслуживание → приёмка production. **Tech Stack:** Next.js, React, TypeScript, Prisma/PostgreSQL, Vitest, браузерные проверки Playwright, Timeweb, ЮKassa, S3.

## 1. Границы работ

**Исключено по просьбе владельца:** весь пункт аудита «Наполнить сайт фактами»: проекты, новости, отчёты, результаты, фотографии, истории, сведения о руководителе/команде, публикация устава и регистрационных документов; переделка главной ради этого наполнения. Пустые разделы не заполнять демонстрационными данными. Существующий функционал публикации сохранить. Сведения о руководителе и регистрационные документы технически не зависят от появления проектов, но здесь также отложены как часть исключённого пункта; это не утверждение, что их нельзя публиковать раньше.

Включены зависимости, доказательства согласий, формы, пояснения банковского перевода, доступность, сопровождение, CI и проверка боевых процессов. Отдельные учётные записи сотрудников — условный последующий этап, если админкой пользуются несколько человек. PDF-каталог отложен вместе с наполнением; текущие HTML и Word остаются.

Варианты организации:

| Подход | Плюсы | Недостатки |
|---|---|---|
| Несколько небольших выпусков — рекомендуется | Каждый выпуск проверяем и откатываем отдельно; внешние доступы не задерживают код | Нужна отдельная приёмка каждого выпуска |
| Один большой выпуск | Одно окно публикации | Сложнее найти причину сбоя и откатить изменения БД/оплаты |
| Только косметические исправления | Быстро | Оставляет зависимости, согласия и эксплуатационные пробелы |

## 2. Порядок и зависимости

1. Подготовка и обновление зависимостей.
2. Согласия: модель БД, сервер, интерфейс, проверки.
3. Доступность форм и ясность QR-переводов.
4. Браузерные проверки для изменений этапов 2–3.
5. Мониторинг, scheduler, резервные копии.
6. Выпуск и боевая приёмка платежей/обращений.
7. Синхронизация документации и закрытие замечаний.

Разработку можно закончить без новых проектов. Сведения о часах работы/условиях помощи публикуются только после получения фактов. Проверка production зависит от доступов и участия владельца, но не блокирует локальные исправления.

## 5. Задача 2 — согласия: минимальная модель доказательств

**Изменить:** `prisma/schema.prisma`, `src/content/legal.ts`, `src/content/donation-offer.ts`.
**Создать:** новую миграцию `prisma/migrations/<timestamp>_consent_evidence/migration.sql`; `src/features/consent/evidence.ts` и `evidence.test.ts` для общей серверной проверки версий.

Предлагаемая модель — поля рядом с существующими сущностями, без отдельной универсальной системы событий:

| Сущность | Новые nullable-поля | Назначение |
|---|---|---|
| ContactRequest | `personalDataConsentVersion String?`, `personalDataConsentAcceptedAt DateTime?` | Версия принятого текста и серверное время |
| Donation | те же два поля + `offerVersion String?`, `offerAcceptedAt DateTime?` | Два независимых подтверждения |

Старые строки остаются `null`: нельзя задним числом создавать доказательство согласия. Для новых успешных записей поля обязательны на уровне прикладной команды. Не добавлять raw IP/user-agent только ради доказательств без определённой цели и срока хранения. Существующий хеш для rate limit не называть юридическим доказательством личности.

- [ ] Сопоставить предлагаемую фиксацию с п. 7.1 согласия; согласовать достаточный минимальный состав. Если требуется изменить текст, версионировать и утвердить документ отдельно до выпуска; не переписывать утверждённые юридические формулировки по собственной инициативе.
- [ ] Описать контракт: клиент присылает факт принятия и увиденную версию; сервер сверяет с текущей опубликованной; время берёт сервер. Не доверять произвольной версии или timestamp клиента.
- [ ] Зафиксировать поведение устаревшей вкладки: отказ до создания записи/платежа с понятной просьбой обновить страницу и повторно ознакомиться; тексты формы по возможности сохранить.

- [ ] Добавить поля и миграцию; проверить на пустой и заполненной тестовой базе, включая сохранение старых строк и статусов.

**Готово:** миграция не уничтожает данные; старые записи явно отличимы от подтверждённых новых; контракт версий одинаков для UI и сервера.

## 17. Условный следующий этап — несколько операторов

Если подтверждён один оператор, текущую общую учётную запись не заменять большой системой пользователей в этом цикле. Если операторов несколько, до расширения доступа составить отдельный план: персональные учётные записи, роли, отзыв доступа, сессии и персональная атрибуция audit. Не пытаться определить сотрудника по IP и не выдавать общий ADMIN за персональный журнал.
