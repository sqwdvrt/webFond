# Приложение фонда: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выпустить приложение фонда «Быть Добру» для iPhone и Android с пятью вкладками и необязательным входом по коду на почту.

**Architecture:** Сайт и его PostgreSQL остаются источником контента. Мобильный клиент получает только публичные данные и данные текущего пользователя через версионированный HTTPS API. Выбор клиента фиксируется после короткой проверки сборок; предварительная рекомендация для экономии работы — отдельный React-клиент с Capacitor, с локально упакованным интерфейсом.

**Tech Stack:** Существующие Next.js, React, TypeScript, Prisma, PostgreSQL, Timeweb S3; кандидат для мобильной части — React, Vite, Capacitor. Версии и совместимость библиотек проверяются на этапе 0, не устанавливаются по памяти.

## Статус и границы

Дата: 13 сентября 2026. Это план этапов с предварительными решениями, а не согласованная до последнего поля спецификация. Этап 0 начат в ветке `codex/mobile-stage-0`, рабочая копия `.worktrees/mobile-stage-0`; журнал — `docs/mobile/progress.md` внутри этой копии. Неотвеченные вопросы не считать согласием.

Подтверждено пользователем:
- iPhone и Android, единый контент с сайтом.
- Нижнее меню ровно в порядке: «Сборы», «Отчет», «Проекты», «Новости», «Профиль».
- Просмотр и пожертвования без регистрации.
- Необязательный вход по коду на электронную почту, без пароля и SMS.
- Push-уведомления могут понадобиться позже, в первой версии их нет.
- Пользователь не пишет код; оформление аккаунтов и юридические сведения остаются за владельцем фонда.
- Сборы — часть проектов, отдельная сущность сборов в первой версии не нужна.
- Профиль: сохраненные сборы, почта и удаление аккаунта. История пожертвований не входит.
- По ответу владельца: Россия; аккаунтов Apple/Google пока нет, планируется оформление; ЮKassa настроена для сайта. Это сообщение владельца, а не результат проверки production.

Предварительные технические решения и оставшиеся допущения:
- «Сборы» — опубликованные проекты с положительной целью сбора; «Проекты» — все опубликованные программы. Отдельных сборов у одного проекта пока нет.
- «Отчет» — опубликованные документы по категориям из существующей админки. Финансовая аналитика по годам и связь отчета с конкретным сбором пока не входят.
- Польза аккаунта в первой версии — синхронизация избранных сборов. История платежей пока не входит.
- Для гостя избранное можно хранить локально; вход нужен для синхронизации. Гостю доступны все пять вкладок, в профиле есть документы и контакты.
- Русский язык, смартфоны; базовая корректность на больших экранах, без отдельного планшетного дизайна. Минимальные версии ОС определяются совместимостью выбранного SDK и реальными устройствами фонда.
- Разовые пожертвования через существующий сайт во внешнем системном браузере; регулярные списания не входят.

## Выбор мобильной технологии

| Вариант | Преимущества | Ограничения | Решение |
|---|---|---|---|
| React + Capacitor, интерфейс внутри приложения | Близко к текущему стеку, можно переиспользовать стили и часть UI, небольшая команда | Проверять WebView, клавиатуру, PDF, защищенное хранение сессии и нативные плагины | Предварительный основной вариант |
| React Native + Expo | Нативные UI-компоненты, удобная база для дальнейших мобильных функций | Разметку и стили сайта придется адаптировать; другой набор зависимостей | Резерв при неудовлетворительной проверке Capacitor |
| Просто открывать сайт в WebView | Быстрый эксперимент | Зависимость от сайта и сети; риск отклонения за недостаточную функциональность | Не считать готовым продуктом |
| Отдельные Swift/Kotlin приложения | Максимальный контроль платформ | Два интерфейса, выше стоимость разработки и сопровождения | Не требуется текущим задачам |

Next.js с серверными страницами, Prisma и обработчиками API нельзя просто положить внутрь мобильной сборки. Сервер остается на хостинге. Мобильный клиент не получает DB/SMTP/платежные ключи. Не обещать прохождение модерации только на основании выбора технологии.

## Организация с учетом лимитов

Снимок до основной части планирования: около 91% пятичасового и 77% недельного лимита осталось. Это общий лимит аккаунта; другие задачи его расходуют. Данные не являются доступным количеством токенов и устаревают в ходе работы.

Расход зависит от модели, объема контекста, сложности и инструментов. Поэтому обещание «все приложение за N токенов» было бы недостоверным. После первых 2–3 рабочих задач сравнить фактический расход и уточнить размер следующих партий. [Официальная документация Codex](https://learn.chatgpt.com/docs/pricing).

- Единица работы: один законченный сценарий с проверкой, обычно 3–6 небольших изменений. Сложные миграции, авторизация и платежи — отдельные задачи.
- Не запускать массово параллельных агентов: это может ускорить время, но увеличить расход. Последовательная работа по умолчанию, отдельная проверка критических изменений при доступности инструментов.
- В начале рабочей партии проверить остатки; при остатке около 20% любого окна закончить текущую небольшую задачу и сохранить результат, не начинать крупный этап. Это рабочий ориентир, не автоматическая гарантия остановки до лимита.
- Каждый этап завершать записью в `docs/mobile/progress.md`: завершенные пункты, ветка/коммит, измененные файлы, команды и результаты проверок, открытые проблемы, следующий конкретный шаг. Ни одного секрета.
- В начале продолжения читать этот план, прогресс и только необходимые файлы; не повторять весь аудит и полные журналы.
- Проверять затронутые сценарии после каждой задачи; полный набор проверок — на интеграционных рубежах. Не экономить на проверках доступа, платежей и удаления аккаунта.
- Модель и тариф без запроса пользователя не менять. Покупку кредитов, сбросы лимитов и внешние платные сервисы автоматически не выполнять.
- При исчерпании лимита работа продолжается после его обновления с сохраненной точки. Автоматическое продолжение по расписанию сейчас не настроено и не обещается.

Оценка ниже — рабочие партии, не число сообщений, не часы и не квота токенов. Базовая оценка: 21–33 партии плюс ориентировочно 25–35% резерва на обнаруженные проблемы. История платежей или отдельная сущность сборов потребуют пересчета. Сроки внешней регистрации и модерации считать отдельно.

**Готово:** тестовый платеж проходит весь путь, отказ не отображается успехом, сайт не регрессирует. Проверочный реальный платеж требует отдельного явного разрешения владельца.

### Этап 6. Приемка и защита данных — 3–5 партий

**Файлы:** `docs/mobile/test-matrix.md`, `docs/mobile/release-checklist.md`, конфигурация проверок в `.github/workflows/` при наличии принятого CI; документы конфиденциальности и согласий сайта после проверки владельцем.

- [ ] Выполнить серверные lint/typecheck/build и релевантные тесты; полный `npm test` на интеграционном рубеже.
- [ ] Выполнить мобильные тесты и production web build; собрать Android release и iOS archive с проверенной конфигурацией подписи.
- [ ] Проверить реальные iPhone и Android плюс симуляторы: холодный старт, фон/возврат, вход, PDF, платежи, плохую сеть и увеличенный текст.
- [ ] Проверить зависимости, отсутствие секретов в сборке/логах, контроль доступа, ограничения OTP и отсутствие персональных данных в публичном S3.
- [ ] Проверить резервное копирование и восстановление на отдельной БД, обратную совместимость миграций и возврат к предыдущей версии API.
- [ ] Согласовать минимальные данные, сроки хранения, обработчиков почты/логов, права на фотографии и тексты. Требования к локализации/передаче данных определяет страна фонда; нужен компетентный ответственный, а не предположение разработчика.

**Готово:** нет открытых критических дефектов, оформлена матрица реальных проверок, ограничения перечислены. Симулятор или браузерный прототип не заменяет проверку банковского возврата на телефоне.

### Этап 7. Магазины и сопровождение — 2–4 партии + внешнее ожидание

**Файлы:** `docs/mobile/store-listing.md`, `docs/mobile/operations.md`, платформенные настройки идентификаторов, подписей и версий.

- [ ] Настроить аккаунты на владельца фонда, роли доступа и сохранность ключей; проверить страну и оплату до назначения даты запуска.
- [ ] Подготовить иконки, скриншоты реальных экранов, описание, поддержку, privacy labels/Data safety, возрастную категорию и доступ для ревью.
- [ ] Провести TestFlight и внутреннее/закрытое тестирование Android. Для новых личных аккаунтов Google проверить применимость требования 12 тестировщиков на 14 непрерывных дней.
- [ ] Перед публикацией сверить актуальные требования SDK и правила магазинов повторно; получить подтверждение владельца на отправку готового релиза.
- [ ] После одобрения выпускать постепенно, наблюдать ошибки, доставку писем и платежи; иметь возможность отключить проблемные платежи серверным флагом.
- [ ] Записать порядок обновления зависимостей, продления членства и сертификатов, восстановления доступа и обработки обращений.

**Готово:** опубликованные версии действительно доступны в выбранных странах. Загруженная сборка или отправка на модерацию еще не означают выпуск. Отказ магазина устраняется отдельной задачей, одобрение не гарантируется.

## Проверочные команды

Серверные команды уже существуют: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run db:validate`. Для узкой задачи использовать `npx vitest run <путь-к-тесту>`; интеграционные платежные тесты — `npm run test:integration:payments` только с изолированной тестовой БД и корректным окружением. Ожидается код завершения 0; пропущенные проверки записывать явно.

Для нового клиента на этапе 0 определить скрипты `lint`, `typecheck`, `test`, `build`, затем запускать `npm --prefix mobile run <script>`. У Capacitor синхронизацию и платформенную сборку выполнять из `mobile/`; конкретные Xcode scheme и Gradle-задачи зафиксировать после генерации, не выдавать неподтвержденные команды за рабочие. При добавлении `mobile/` проверить исключения корневых TypeScript/ESLint и deployment build context, чтобы сервер не пытался собирать мобильный код.

Каждую рискованную задачу дробить: тест нужного поведения → воспроизведение ожидаемого отказа → минимальная реализация → успешная проверка → запись результата. Не писать тесты, которые лишь повторяют верстку. Коммиты делать небольшими и только с относящимися к задаче файлами.

## Реестр рисков

P0 — блокирует выпуск или угрожает деньгам/доступу; P1 — существенная проблема; P2 — управляемое ухудшение. Это основные выявленные и предполагаемые риски, не обещание перечислить все будущие проблемы.

| Риск | Уровень | Снижение риска и момент проверки |
|---|---|---|
| Недоступна регистрация/оплата аккаунта в стране фонда | P0 | Проверка на этапе 0; принадлежность аккаунтов фонду; не обещать дату до подтверждения. Другой канал Android не решает публикацию iOS. |
| Правила благотворительных платежей Apple | P0 | Проверить статус фонда и регионы; базово внешний Safari, не встроенная форма. Условия прямого сбора внутри приложения проверять отдельно. |
| Утечка данных/захват аккаунта | P0 | Одноразовые коды, лимиты, защищенные сессии, изоляция ролей, тесты чужого доступа, отсутствие секретов в клиенте. |
| Показ чужих пожертвований | P0 | Не связывать платежи только по email; история только после безопасной серверной привязки. |
| Двойной платеж или неверная сумма | P0 | Идемпотентность, серверный статус, тесты повторных webhook, суммы в копейках, исключение двойного учета ручных сумм. |
| Миграция нарушает сайт или теряет данные | P0 | Добавочные миграции, отдельная БД для тестов, проверенное восстановление, резервная копия и план отката. |
| Недопустимая обработка персональных данных | P0 | До production определить страну, хранение, провайдеров и основания обработки с ответственным фонда; минимум данных. |
| Отклонение как переупакованного сайта | P1 | Полезные мобильные сценарии, избранное, системные действия, полноценные состояния; оценить прототип до всей реализации. |
| Отсутствие удаления аккаунта/неверные privacy labels | P1 | Удаление в приложении и веб-запрос, точная декларация реально используемых SDK. |
| Почта попадает в спам, OTP дорого атаковать | P1 | SPF/DKIM/DMARC, проверка доставки, ограничение запросов и расходов, наблюдение ошибок провайдера. |
| Вход без полезного профиля усложняет продукт | P1 | Избранное с синхронизацией; гостевой доступ сохраняется; не добавлять личные поля без сценария. |
| Сервер обновился, старое приложение сломалось | P1 | API v1, добавочные изменения DTO, тесты совместимости, отсутствие принудительного одновременного релиза. |
| Устаревший прогресс/закрытый сбор из кэша | P1 | Явная давность, обновление перед платежом, серверная проверка возможности пожертвования. |
| Небезопасный HTML/ссылка/PDF | P1 | Санитизация контента, ограничение URL-схем и доменов, типов и размеров; не исполнять произвольный контент CMS. |
| Чувствительные данные подопечных в фото/отчетах | P1 | Проверка прав и согласий до публикации, исключение лишних данных, политика удаления файлов и кэша. |
| СБП/браузер не возвращает в приложение | P1 | Реальные устройства, fallback на сайт, отсутствие ложного статуса успеха, повторное получение состояния. |
| Нет SDK/сертификатов/реальных тестовых устройств | P1 | Инвентаризация на этапе 0; не откладывать первую платформенную сборку до конца. |
| Поломка сайта из-за новой папки/зависимостей | P1 | Раздельный пакет клиента, проверка корневых конфигураций и Timeweb build. |
| Нагрузка на БД, тяжелые изображения и документы | P1 | Пагинация, индексы по реальным запросам, лимиты, оптимизация изображений и проверка медленной сети. |
| Лимиты Codex прерывают задачу | P1 | Небольшие партии, письменный прогресс, резерв, отсутствие обещания завершить за одно окно. |
| Зависимость от единственного владельца ключей | P1 | Аккаунты фонда, контролируемое хранение ключей, восстановление и минимальные роли. |
| Рост объема: несколько сборов, история, подписки | P1 | Согласовать развилки до схемы БД; отдельные этапы и пересчет объема. |
| Задержка модерации/обязательного тестирования | P1 | Внешнее ожидание отдельно от разработки, подготовить тестировщиков заранее. |
| Смена SDK, прекращение поддержки плагина | P1 | Совместимые поддерживаемые версии, фиксация зависимостей и регулярное обслуживание. |
| Мелкие экраны, доступность, обрезанные подписи | P2 | Пять стабильных слотов меню, тест крупного текста и экранных дикторов. |
| Нет контента к запуску | P2 | Владелец готовит реальные материалы; пустые состояния, отсутствие вымышленных сумм и отчетов. |
| Растут расходы почты/сервера/сборок | P2 | Учесть регулярные расходы, ограничить OTP, выбрать провайдеров после проверки тарифов и географии. |

## Будущие уведомления

Сейчас достаточно стабильных идентификаторов материалов и структуры ссылок на детали. Не создавать заранее таблицы push-токенов и фоновые очереди. ## Источники и ограничения проверки

- [Capacitor](https://capacitorjs.com/docs) и [Expo](https://docs.expo.dev/) — доступные варианты мобильного клиента; выбор здесь является инженерной рекомендацией для этого проекта.
- [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), разделы 3.2.1(vi), 3.2.2(iv), 4.2 и 5.1.1: благотворительные платежи, полезность приложения и учетные записи. Для прямого сбора одобренными НКО есть дополнительные условия, включая Apple Pay; их применимость нельзя предполагать.
- [Удаление аккаунта Apple](https://developer.apple.com/support/offering-account-deletion-in-your-app) и [Google](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).
- [Тестирование новых личных аккаунтов Google](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en-GB): применимость зависит от вида и даты создания аккаунта.
- [Расход лимитов Codex](https://learn.chatgpt.com/docs/pricing): планирование по небольшим задачам, а не фиктивно точной квоте токенов.

Источники проверены при планировании 13 сентября 2026; повторно сверить перед релизом. Production, реальные письма, платежи и нативные сборки в этой задаче не проверялись. Юридическая применимость и географическая доступность пока открыты. План проверен автором на зависимости, критерии приемки и согласованность; независимый агент-ревьюер в доступных инструментах отсутствует.
