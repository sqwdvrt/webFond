# План улучшения публичного сайта

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сделать пожертвования понятнее, улучшить мобильную доступность и показать проверяемые сведения о фонде.

**Architecture:** Сохранить текущие страницы, компоненты и серверные источники данных. Выполнять этапы независимо; подключение платежей и изменение инфраструктуры не входят в визуальные правки. Использовать существующую административную публикацию документов и проектов.

**Tech Stack:** Next.js App Router, React, TypeScript, Prisma, Vitest, Testing Library, CSS.

Исходные результаты 1291/12 предоставлены пользователем. Этапы реализованы и локально проверены; актуальные результаты, изменения локальной БД и внешние условия выпуска приведены в [итоговой сводке](2026-10-19-public-site-release-summary.md). Чек-листы ниже сохраняют исходную формулировку плана; состояние выполнения следует смотреть в сводке.

## Этап 1. Установить причину readiness 503

Файлы: `src/app/api/ready/route.ts`, `src/features/readiness/evaluate.ts`, `src/lib/admin-auth/config.ts`, `src/app/api/ready/route.test.ts`, `README.md`.

- [ ] Проверить требования `readAdminAuthConfig` и наличие необходимых настроек локально и в целевой среде, не выводя значения секретов.
- [ ] Зафиксировать: текущая readiness-проверка проверяет конфигурацию admin-auth; предположение о причине в DATABASE_URL пока не подтверждено.
- [ ] Отдельно проверить подключение к базе и статус миграций в целевой среде. Не применять миграции к production в рамках диагностики.
- [ ] Проверить, какой endpoint использует платформа для проверки живости и готовности; описать назначение `/api/health` и `/api/ready` в README. Не маскировать неготовность постоянным 200.
- [ ] Если потребуется изменение поведения, сначала добавить регрессионный тест к существующим тестам readiness, затем исправить причину.

Проверка: `npx vitest run src/app/api/ready/route.test.ts src/app/api/health/route.test.ts`; сверить ответы обоих endpoint с конфигурацией среды.

Результат: причина 503 установлена, необходимая конфигурация и правила проверки платформой документированы. Если доступа к среде нет, зафиксировать оставшуюся проверку как условие деплоя.

- [ ] Уменьшить мобильные отступы hero и размер логотипа; использовать короткий подзаголовок только на главной, не сокращая глобальное SEO-описание без необходимости.
- [ ] Сделать «Нужна помощь» заметной и удобной для касания; проверить, что заголовок и оба действия находятся до крупного декоративного блока.
- [ ] Выбрать семантику меню по фактическому поведению: для модального меню обеспечить фокус внутри, недоступность фона и корректную семантику; для раскрывающейся навигации сохранить обычный порядок Tab. Не добавлять ловушку фокуса автоматически.
- [ ] Добавить возврат фокуса на кнопку после Escape и закрытия фоном; при переходе на другую страницу согласовать фокус с навигацией, не возвращать его безусловно.
- [ ] Проверить закрытие текущей ссылкой, Escape, кнопкой и фоном; видимый фокус, текущий раздел и поведение при смене ширины экрана.
- [ ] Добавить тесты клавиатурного поведения перед изменением логики и повторить их после.

Проверка: `npx vitest run src/components/layout/site-header.test.tsx src/app/hero-logo-styles.test.ts src/app/page.test.tsx`; ручной проход Tab/Shift+Tab/Escape и проверка при увеличении текста.

Результат: компактный первый экран без горизонтальной прокрутки; меню полностью управляется клавиатурой.

Файлы: `src/app/page.tsx`, `src/config/site.ts`, `src/app/reports/page.tsx`, `src/features/content-admin/repository.ts` (переиспользовать существующие выборки), `src/app/page.test.tsx`, `src/app/reports/reports-page.test.tsx`.

- [ ] Вынести на главную заметный блок с ОГРН, ИНН и ссылками на реквизиты и отчёты.
- [ ] Добавить краткий блок «На что идут пожертвования» на основании действующей оферты и подтверждённых направлений деятельности.
- [ ] Показывать реальные проекты, статусы и суммы только при наличии проверенного источника. Не путать поступления, целевую сумму и фактические расходы.
- [ ] Показывать дату обновления конкретных сведений из источника, а не текущую дату открытия страницы.
- [ ] При отсутствии материалов использовать честное пустое состояние; при сбое источника сохранить доступность главной и статических реквизитов.
- [ ] Добавить проверки опубликованных данных, отсутствия материалов и ошибки источника. Не менять схему БД, если существующих данных достаточно.

Проверка: `npx vitest run src/app/page.test.tsx src/app/reports/reports-page.test.tsx`; вручную проверить документы, ссылки и соответствие чисел источникам.

Результат: каждый факт о работе фонда можно проверить. Полнота этого этапа зависит от наличия реальных материалов фонда.

- [ ] Запустить `npm run verify`: тесты, lint, TypeScript, Prisma validate, production build и проверка diff должны завершиться успешно.
- [ ] Проверить публичные маршруты в production-режиме и отсутствие новых предупреждений в консоли браузера.
- [ ] Повторить основные пути: пожертвование при включённой и отключённой онлайн-оплате, получение помощи, скачивание QR, открытие отчётов, мобильное меню.
- [ ] Проверить целевую среду: конфигурацию admin-auth, доступность БД, миграции и настройки проверок платформы. Не включать оплату только ради успешного smoke-теста.

Результат: изменения проверены, известны зависимости от контента и инфраструктуры, пакет готов к выпуску.

## Порядок и границы

Рекомендуемый порядок: 1 → 2 → 3 → 4 → 5 → 6. Сбор документов для этапа 5 можно начать сразу. Каждый этап оформлять отдельным небольшим изменением; не включать переработку административной панели, новую платёжную интеграцию и полную смену дизайна.
