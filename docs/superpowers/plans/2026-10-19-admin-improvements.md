# Admin Improvements Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сделать работу администратора надёжной: корректная сверка платежей, сохранность введённых данных, понятная публикация, удобный поиск и наблюдаемая история действий.

**Architecture:** Развивать существующий Next.js App Router и серверные mutations/repositories. Платёжную сверку исправить отдельно от редакторских функций; общие компоненты форм внедрять постепенно. Сохранить текущие проверки авторизации, валидацию, optimistic concurrency через `updatedAt`, обработку статусов и запрет удаления ранее опубликованных материалов.

**Tech Stack:** TypeScript, React, Next.js, Prisma/PostgreSQL, CSS Modules, Vitest, Testing Library; существующий YooKassa client.

Реализация подготовлена в ветке `codex/admin-improvements`. Выполнены изменения
кода по этапам 1–9: очередь и ручная сверка, диагностика, защита форм,
предпросмотр/публикация, списки, загрузки, реквизиты, обращения, обзор и аудит.
Чек-листы ниже сохранены как исходные требования; результаты проверок и границы
выпуска перечислены здесь.

- Общий набор: 1435 тестов прошли, 12 пропущены существующей конфигурацией.
- Отдельная локальная PostgreSQL: 15 интеграционных платёжных тестов прошли,
  включая конкурирующие claim, истечение lease и очередь из 60 исчерпанных записей.
- TypeScript, ESLint и валидация Prisma проходят.
- Браузер: создание черновика, ошибка валидации с сохранением текста, последующее
  успешное сохранение и уход без ложного предупреждения; списки и мобильные фильтры
  без горизонтального переполнения при ширине 390 px.
- Добавлена миграция `20261019090000_admin_workflow_audit`, проверенная на локальной
  тестовой БД. Секреты и данные production не использовались.
- Production-миграция, деплой, расписание Timeweb и сверка настоящего платежа
  требуют отдельного запуска в боевом окружении; здесь они не выполнялись.
- Предупреждение об уходе поддерживает ссылки, закрытие/перезагрузку вкладки,
  выход из админки и отправку других форм. Блокировка SPA «назад/вперёд» через
  недокументированный роутер и автоматическое сохранение не добавлялись.

- [ ] Перенести условия отбора в SQL/Prisma до `take`: `PENDING`, задан provider ID, `manualReviewRequired=false`, наступило `nextReconcileAt`, lease отсутствует или истёк, число попыток меньше лимита и возраст в допустимом диапазоне. Отбор подходящих записей не зависит от завершения отдельной очистки очереди. Разделить возраст платежа и порог начала проверки; устранить неоднозначное имя `olderThan`.
- [ ] Переводить исчерпавшие попытки/возраст записи в `manualReviewRequired=true`, оставляя финансовый статус неизменным. Выполнять это отдельной ограниченной операцией так, чтобы такие записи перестали занимать очередь.
- [ ] Проверить тестом очередь, где исчерпавших лимиты записей больше размера batch очистки: подходящий платёж должен обрабатываться в этом же запуске.
- [ ] Зафиксировать начальную политику: автоматический запуск раз в 5 минут, проверка платежей старше 5 минут, batch 25, backoff до часа, максимум 8 попыток, возраст автоматической сверки до 90 дней. Возраст свыше 90 дней допускается для явно выбранной ручной проверки.
- [ ] Проверить ограничение времени выполнения job: конечный таймаут provider GET, ограничение общего времени batch; lease получать непосредственно перед запросом, освобождать в `finally` при доступной БД. Не держать SQL-транзакцию во время сетевого запроса.
- [ ] Учитывать гонку webhook и batch: после условного обновления проверять фактический терминальный статус. `SUCCEEDED` нельзя считать результатом, если конкурентно сохранён `CANCELED`, и наоборот.
- [ ] Сохранять точный фиксированный `alertCode` постоянной ошибки, а не общий `payment_reconcile_permanent_rejection`. При недоступной БД возвращать retryable outcome без обещания сохранённой диагностики.
- [ ] Валидировать запросы: только JSON-объект, конечный целый `limit` от 1 до 100; отклонять `null`, массивы, дроби, отрицательные и слишком большие значения. Проверять авторизацию до обработки данных.
- [ ] Подтвердить атомарность claim на отдельной тестовой PostgreSQL: два исполнителя, истёкшая lease, webhook во время сверки, восстановление после аварийного завершения.

**Инвариант:** финальный статус меняется только по проверенному ответу YooKassa с совпавшими ID, metadata, суммой и валютой; для успеха обязательны `paid` и дата подтверждения. Статус не выставляется по возрасту, сообщению браузера или нажатию кнопки.

## Критерии готовности

1. Очередь не застревает на старых/исчерпавших попытки платежах; исходы webhook и ручной сверки согласованы.
2. Оператор видит последнюю проверку и может безопасно повторить её для выбранной записи.
3. После проверки таблица обновляется, причины проблем понятны.
4. Формы предупреждают о потере данных и не сохраняются посреди загрузки файла.
5. Предпросмотр совпадает с публичным отображением и не публикует черновик.
6. Списки контента ограничены серверной пагинацией и поддерживают поиск/фильтры.
7. Публичные изменения и административные команды отражаются в истории без чувствительных payload.
8. Работа автоматической сверки в production подтверждена отдельно от готовности кода.
