# Этап 3. Единая админка контента

## Цель

Завершить оставшийся пункт этапа 3: из существующей защищенной административной
части управлять проектами, новостями, документами и реквизитами. Публичные
страницы показывают только явно опубликованный контент.

## Границы работы

- Сохраняется одна точка входа `/admin`, одна admin-сессия и один визуальный
  рабочий интерфейс.
- Разделы проектов, новостей, документов, реквизитов и пожертвований находятся
  внутри общего защищенного layout и общей навигации.
- Управление пользователями, роли, медиахранилище, rich-text редактор, история
  версий и платежный контур в эту работу не входят.
- Изображения и PDF задаются проверенными URL. Загрузка бинарных файлов на сервер
  не добавляется.

## Навигация и маршруты

Общий admin-shell содержит название фонда, текущую учетную запись, выход и
навигацию:

- `/admin` — обзор разделов;
- `/admin/projects` — список проектов и создание;
- `/admin/projects/[id]` — редактирование проекта;
- `/admin/news` и `/admin/news/[id]` — новости;
- `/admin/documents` и `/admin/documents/[id]` — документы;
- `/admin/requisites` — единственная форма реквизитов;
- `/admin/donations` — существующий список пожертвований.

Это не отдельные админки: все маршруты используют существующий protected layout,
одну сессию, один header и одни UI-паттерны. На мобильном экране навигация
становится горизонтально прокручиваемой строкой, формы складываются в одну
колонку, а таблицы прокручиваются только внутри своей области.

## Модель публикации

Для проектов, новостей и документов используются статусы `DRAFT`, `PUBLISHED`,
`ARCHIVED`:

- `DRAFT` никогда не виден публично;
- `PUBLISHED` виден публично;
- `ARCHIVED` хранится в админке, но не виден публично.

При первом переходе в `PUBLISHED` задается `publishedAt`. Эта дата больше не
очищается: статус определяет текущую видимость, а сохраненная дата позволяет
отличить никогда не опубликованный черновик от ранее опубликованной записи.
Публичные списки сортируются по `publishedAt DESC`, затем по `id DESC`.

Модели `Project` и `NewsPost` уже содержат нужные поля. В `Document` добавляется
`status PublicationStatus @default(DRAFT)` и индекс `(status, publishedAt, id)`.
Миграция сначала добавляет nullable-колонку, помечает существующие строки с
непустым `publishedAt` как `PUBLISHED`, остальные как `DRAFT`, и только затем
добавляет `NOT NULL` и default. Миграционный тест начинает с обеих разновидностей
существующих строк и проверяет сохранение их видимости. Для проектов и новостей
добавляются такие же индексы публичной выборки.

Реквизиты хранятся в `SiteSetting` с ключом `requisites`. Значение имеет
версионированную JSON-структуру:

```ts
type RequisitesSetting = {
  version: 1;
  status: "DRAFT" | "PUBLISHED" | "ARCHIVED";
  fullName: string;
  shortName: string;
  ogrn: string;
  inn: string;
  kpp: string;
  address: string;
  email: string;
  bankName: string;
  recipientName: string;
  checkingAccount: string;
  correspondentAccount: string;
  bik: string;
};
```

До первой записи форма заполняется подтвержденными юридическими значениями из
`siteConfig`, а банковские поля остаются пустыми. Значение проходит runtime-
валидацию на каждом чтении. Неизвестная версия, неверный тип или отсутствующее
поле не используются: публичная страница закрыто откатывается к подтвержденным
`siteConfig` и пустому банковскому состоянию, а админка показывает
восстанавливаемую нейтральную ошибку и не отображает непроверенные значения.
Публичная страница использует настройку только в статусе `PUBLISHED`.

## Поля и валидация

### Проекты и новости

- `title`: обязательная строка, 2-160 символов;
- `slug`: обязательный lowercase slug, 2-120 символов, только `a-z`, `0-9` и
  одиночные дефисы, уникален внутри своей модели;
- `summary`: необязательная строка до 500 символов;
- `content`: необязательный plain text до 20 000 символов;
- `imageUrl`: необязательный абсолютный `https` URL либо локальный путь,
  начинающийся с `/`;
- `status`: только один из трех статусов публикации.

Черновик или архив можно сохранить без `summary` и `content`. Публикация требует
`summary` длиной 10-500 символов и `content` длиной 20-20 000 символов, чтобы
публичная карточка и detail-страница всегда имели содержимое.

### Документы

- `title`: 2-160 символов;
- `category`: 2-80 символов;
- `fileUrl`: обязательный абсолютный `https` URL либо локальный путь;
- `status`: один из трех статусов.

Все URL ограничены 2048 символами. Локальный путь начинается ровно с одного `/`,
не содержит обратных слешей или управляющих символов и поэтому не допускает
форму `//host/path`. Внешний URL использует только `https:`, не содержит
username/password и разбирается стандартным `URL`. Сервер не загружает и не
проверяет содержимое произвольных URL. Документы называются ссылками на документ,
а не гарантированными PDF, пока формат не подтвержден внешним хранилищем.

### Реквизиты

Сначала все значения обрезаются по краям, затем проверяются обязательность,
длина и формат. Для `DRAFT` и `ARCHIVED` банковские поля могут быть пустыми;
`PUBLISHED` требует все поля из таблицы:

| Поле | Ограничение после trim |
| --- | --- |
| `fullName` | обязательно, 2-240 символов |
| `shortName` | обязательно, 2-160 символов |
| `ogrn` | обязательно, ровно 13 цифр |
| `inn` | обязательно, ровно 10 цифр |
| `kpp` | обязательно, ровно 9 цифр |
| `address` | обязательно, 5-500 символов |
| `email` | обязательно, 3-254 символа, один `@`, непустые части |
| `bankName` | при публикации обязательно, 2-200 символов |
| `recipientName` | при публикации обязательно, 2-240 символов |
| `checkingAccount` | при публикации обязательно, ровно 20 цифр |
| `correspondentAccount` | при публикации обязательно, ровно 20 цифр |
| `bik` | при публикации обязательно, ровно 9 цифр |

Юридические поля обязательны при любом сохранении. Черновик можно сохранить с
пустыми банковскими полями, но каждое заполненное поле все равно проверяется.

Неизвестные поля формы игнорируются. Ошибки валидации возвращаются рядом с
формой без записи в базу. Конфликт slug показывается нейтральным сообщением и не
раскрывает детали Prisma.

## Серверные границы

- Каждое server action самостоятельно вызывает `requireAdminSession()` до
  разбора формы и обращения к базе.
- Доступ к данным изолирован в репозиториях; React-компоненты не собирают Prisma
  запросы.
- Создание, изменение и удаление выполняются server actions. Обновление и
  удаление передают `updatedAt` как optimistic-lock token. Репозиторий изменяет
  запись только по паре `id + updatedAt`; для `SiteSetting` используется
  `key + updatedAt`. Нулевое число измененных строк означает удаленную или более
  новую версию: форма получает нейтральный конфликт без записи и redirect.
  Несуществующий admin edit ID вызывает `notFound()`.
- Hard delete разрешен сервером только для `DRAFT` с `publishedAt = null`, то
  есть никогда не опубликованного черновика. Ранее опубликованный материал можно
  только перевести в `ARCHIVED`. Requisites-setting не удаляется. UI требует
  подтверждение и не показывает недопустимую команду удаления.
- После проекта revalidate получает `/admin/projects`, `/projects`, старый detail
  path и новый detail path при смене slug. После новости аналогично обновляются
  `/admin/news`, `/news`, старый и новый detail path. Архивация и удаление всегда
  обновляют старый detail path. Документы обновляют `/admin/documents` и
  `/reports`, реквизиты — `/admin/requisites` и `/requisites`. Любое изменение
  публикации проекта или новости также обновляет `/sitemap.xml`. После этого
  выполняется redirect с коротким success-параметром.
- Admin-ответы продолжают получать существующие privacy headers. В собственные
  журналы не записываются содержимое форм, реквизиты или Prisma payload.

## Публичные страницы

- `/projects` сохраняет существующий уставный список и ниже показывает карточки
  опубликованных проектов; при отсутствии записей дополнительный блок не
  выводится.
- `/projects/[slug]` показывает опубликованный проект или `notFound()`.
- `/news` показывает опубликованные новости либо существующее пустое состояние.
- `/news/[slug]` показывает опубликованную новость или `notFound()`.
- `/reports` группирует опубликованные документы по категории и выводит ссылки
  на PDF; при отсутствии документов сохраняет пустое состояние.
- `/requisites` показывает опубликованные юридические и банковские данные. Пока
  настройка не опубликована, текущие подтвержденные юридические строки остаются,
  а банковский блок остается пустым.

При ошибке БД collection-страницы отличают ее от пустой выборки. `/projects`
сохраняет уставный блок, `/requisites` сохраняет подтвержденный fallback, а
динамические секции показывают временную нейтральную ошибку. Ошибка detail-запроса
передается локальному error boundary и не превращается в `notFound()`.

Пользовательский текст отображается как текст с сохранением абзацев, без
`dangerouslySetInnerHTML`. Изображения используют существующий Next Image только
для локальных путей; внешние URL отображаются обычным `img` с безопасным alt,
чтобы не расширять список доверенных image-hosts.

Коллекции `/news` и `/reports` снимают placeholder `noindex`, когда имеют хотя бы
одну опубликованную запись; при пустой выборке или сбое остаются `noindex`.
Detail-страницы генерируют title, description и canonical только для
опубликованной записи. Sitemap включает опубликованные `/projects/[slug]` и
`/news/[slug]`, не включает admin, черновики, архив или внешние document URL.

## Интерфейс админки

Списки компактны и предназначены для повторной работы: заголовок, статус, дата
изменения, команда редактирования и кнопка создания. Формы используют обычные
поля, textarea, select статуса и явные команды «Сохранить» и «Удалить». Статусы
показываются текстом и цветом, но цвет не является единственным сигналом.

У каждой страницы есть нейтральное пустое состояние и локальная обработка
ошибки базы. Кнопки блокируются на время server action. После сохранения
интерфейс показывает короткий success-status, доступный screen reader.

## Проверки

- тест миграции, индексов и generated Prisma schema;
- unit-тесты строгой валидации всех форм и переходов статусов;
- repository-тесты выборки только `PUBLISHED`, сортировки и CRUD;
- action-тесты auth-first, отсутствия записи при ошибке, revalidation и redirect;
- тесты optimistic locking, ограничения удаления и инвалидации старого/new slug;
- component-тесты списков, форм, ошибок и подтверждения удаления;
- public page-тесты draft/archived exclusion, published rendering и `notFound`;
- тесты malformed requisites JSON, fail-closed fallback, metadata и sitemap;
- Axe-проверки заполненного и пустого admin-интерфейса;
- полный `npm test`, lint, typecheck, Prisma validate/generate, migration deploy,
  production build и `git diff --check`;
- browser QA desktop/mobile: создание черновика, публикация, публичное
  отображение, редактирование, архивирование, удаление, PDF-ссылка и реквизиты.

## Критерии готовности

- Все четыре типа контента управляются из одной существующей админки.
- Публично виден только статус `PUBLISHED`.
- Черновики и архив не доступны по прямому публичному URL.
- Проекты, новости, документы и реквизиты отражаются на соответствующих
  публичных страницах после публикации.
- Неавторизованный пользователь не может читать admin-страницы или выполнять
  server actions.
- Миграция применяется к локальной PostgreSQL, а основной CRUD-сценарий проходит
  в браузере без ошибок консоли и переполнения layout.
