# Этап 4. Разовые пожертвования через ЮKassa и СБП

## Цель

Добавить безопасный сценарий разового анонимного пожертвования через СБП:
создание платежа в ЮKassa, переход на динамический QR, обработку webhook,
сверку статуса, защиту от повторов и понятный результат для пользователя.

Реальный платеж и доставка production-webhook не входят в приемку без тестовых
`shopId` и `secretKey`. До получения доступов внешний контракт проверяется
детерминированными тестами с подмененным HTTP-транспортом.

## Принятые продуктовые решения

- Доступны суммы 300, 500, 1 000, 3 000 и 5 000 рублей.
- Пользователь может указать другую целую сумму от 100 до 100 000 рублей.
- Пожертвование анонимное: имя, email и телефон не запрашиваются и не передаются.
- Перед отправкой обязательно явное принятие оферты пожертвования.
- Платежная форма и create route остаются выключенными до публикации проверенной
  оферты и явного `PAYMENTS_ENABLED=true`. Источник юридического контента
  экспортирует машинные `status: "placeholder" | "published"` и `version`.
  Конфигурация требует `status = "published"` и точного совпадения version с
  `PAYMENTS_OFFER_VERSION`. Текущая страница-заглушка имеет
  `status: "placeholder"` и не может открыть платежный контур.
- Согласие на обработку персональных данных в платежной форме не показывается,
  поскольку форма не собирает персональные данные.
- Объект `receipt` не передается. Владелец подтвердил, что фискальный чек для
  этого сценария пожертвования не требуется.
- Подписки, автоплатежи, сохранение платежного метода и двухстадийная оплата не
  используются.

## Архитектура

Платежный контур оформляется отдельным модулем `src/features/payments`. Публичная
форма и HTTP-маршруты не содержат Prisma-запросов и деталей API ЮKassa. Создание
платежа, webhook и страница результата используют общий сервис сверки статуса.

Основные единицы:

- `config.ts` — строгая server-only конфигурация ЮKassa и публичного URL сайта;
- `validation.ts` — нормализация суммы, ключа попытки и принятия оферты;
- `yookassa-client.ts` — минимальный клиент `createPayment` и `getPayment` поверх
  встроенного `fetch`;
- `repository.ts` — создание и поиск `Donation`, привязка provider ID, удаление
  однозначно отклоненного черновика и условные переходы статуса;
- `rate-limit.ts` — PostgreSQL-backed лимиты всех запросов и новых попыток по
  HMAC client key, а также общие предохранительные лимиты;
- `reconcile.ts` — проверка удаленного платежа и единственное место обновления
  локального статуса;
- `create-payment.ts` — оркестрация создания или безопасного повтора попытки;
- route handlers — тонкие HTTP-адаптеры с внедряемыми зависимостями для тестов.

SDK ЮKassa не добавляется: для этапа нужны только два REST-метода, а прямой
`fetch` позволяет явно проверить Basic Auth, JSON и `Idempotence-Key`.

Существующая модель `Donation` уже содержит платежные ограничения:
`idempotenceKey` и `providerPaymentId` уникальны, сумма хранится в копейках,
статусы ограничены `PENDING`, `SUCCEEDED`, `CANCELED`. Необязательные
`donorName` и `donorEmail` остаются пустыми. Отдельная миграция добавляет только
операционную таблицу короткоживущих rate-limit buckets; она не связывается с
`Donation` и не хранит исходный адрес клиента.

## Создание платежа

Рабочая форма заменяет заглушку на `/help`. Она содержит фиксированные суммы,
поле своей суммы, ссылку на оферту, обязательный checkbox и кнопку «Оплатить
через СБП». Форма доступна с клавиатуры, сообщает ошибки рядом с полями и
блокирует повторное нажатие во время запроса.

Для каждой новой пользовательской попытки браузер создает UUID v4 и сохраняет в
`sessionStorage` объект `{ id, amountRoubles, createdAt }`. Reload, Back и повтор
после сетевой ошибки используют тот же объект, если сумма не изменилась и возраст
меньше 23 часов. Попытка очищается после терминального результата или явной
команды «Начать новый платеж». Изменение суммы требует подтвержденного начала
новой попытки. После 23 часов stale-UUID сохраняется, автоматический POST и
автоматическая замена UUID запрещены. UI объясняет неопределенный исход и требует
явно подтвердить «Начать новый платеж», поскольку старый платеж теоретически мог
успеть создаться. Официальное окно идемпотентности ЮKassa равно 24 часам, и
бесшумный повтор за его пределами может создать второй платеж.

Сервер принимает JSON с суммой в рублях, признаком принятия оферты, UUID и
honeypot-полем, затем проверяет feature gate, `Origin`, `Content-Type`, размер
тела и значения полей. Пустой honeypot, same-origin и DB rate limit вместе
составляют защиту формы от спама.

`POST /api/payments/create` выполняет следующие действия:

1. Загружает и проверяет конфигурацию до записи в БД.
2. В одной Prisma-транзакции расходует per-client и global лимиты всех запросов,
   находит попытку и при необходимости расходует лимиты новых UUID одновременно
   с созданием `Donation`.
3. Находит или создает `Donation(PENDING)` с UUID в `idempotenceKey`.
4. Вызывает `POST https://api.yookassa.ru/v3/payments` с Basic Auth и тем же
   UUID в заголовке `Idempotence-Key`.
5. Передает сумму с двумя десятичными знаками, валюту `RUB`,
   `payment_method_data.type = "sbp"`, `confirmation.type = "redirect"`,
   `capture = true`, серверный `return_url`, безопасное описание и
   `metadata.donationId`.
6. Проверяет ответ, привязывает уникальный `providerPaymentId` и возвращает
   браузеру разрешенный HTTPS `confirmation_url`.

Если UUID уже существует, сумма и валюта должны совпадать с исходной записью.
При гонке двух create-запросов проигравший уникальный insert перечитывает запись
и применяет ту же проверку. Привязка provider ID условна: поле может измениться
только из `null` в конкретный ID или подтвердить уже сохраненный тот же ID.
Другой ID считается конфликтом и не перезаписывается.

При наличии provider ID сервер получает актуальный платеж и возвращает его
confirmation URL либо URL локального результата для терминального статуса. Если
provider ID еще не сохранен, POST повторяется с тем же ключом: идемпотентность
ЮKassa должна вернуть результат исходной операции, в том числе после сетевого
сбоя между ответом провайдера и записью в БД. Такой повтор разрешен только пока
локальная запись моложе 23 часов; более старая попытка получает `409 stale_attempt`
и UI предлагает явно начать новый платеж.

После ответа create API и условной привязки provider ID оркестратор всегда
перечитывает `Donation`. Если ранний webhook уже сделал запись терминальной,
create route возвращает локальный result URL, а не устаревший confirmation URL.

Rate limit использует фиксированные UTC-окна и модель:

```prisma
model PaymentRateLimitBucket {
  key         String
  windowStart DateTime
  count       Int
  expiresAt   DateTime

  @@id([key, windowStart])
  @@index([expiresAt])
}
```

Ключ включает scope и длительность окна. В одной интерактивной транзакции
атомарный PostgreSQL upsert с increment возвращает новое значение счетчика.
Лимиты: 20 любых create-запросов на client key за 10 минут, 5 новых UUID на
client key за 10 минут, 300 любых запросов глобально за минуту и 100 новых UUID
глобально за минуту. Проверка существования UUID, расход обоих new-attempt
buckets и создание `Donation` находятся в той же транзакции. Поэтому два
конкурентных запроса не создают две записи и не считают один UUID дважды.
Истекшие buckets удаляются opportunistic cleanup после основной транзакции.

Однозначный 4xx ЮKassa означает, что платеж не принят: непривязанный локальный
черновик удаляется. При timeout, сетевой ошибке или 5xx исход операции не
считается известным, поэтому `PENDING` сохраняется для безопасного повтора.

## Страница результата

Базовый `YOOKASSA_RETURN_URL` не содержит query или fragment и имеет точный путь
`/donation/result`. Сервер копирует URL и добавляет единственный query-параметр
`donation=<localDonationId>`. Идентификатор является только
ссылкой на анонимную запись; страница не показывает provider ID или технические
данные.

Если у записи есть provider ID, страница вызывает общий сервис сверки перед
рендерингом. Отображаются четыре состояния:

- `SUCCEEDED` — благодарность и подтверждение принятого пожертвования;
- `CANCELED` — спокойное сообщение, что платеж не завершен, и ссылка повторить;
- `PENDING` — платеж еще обрабатывается, предложение обновить страницу;
- техническая ошибка или неизвестный ID — нейтральная страница ошибки без
  раскрытия внутренней информации.

Терминальный результат удаляет сохраненную браузерную попытку. Маршрут
принудительно динамический и отдает `noindex`, `no-store`,
`Referrer-Policy: no-referrer` и `X-Content-Type-Options: nosniff`.

## Webhook и сверка статуса

`POST /api/payments/webhook` принимает только события `payment.succeeded` и
`payment.canceled`. Входной объект служит сигналом, но не источником истины.
Перед изменением БД сервер выполняет авторизованный GET
`/v3/payments/{paymentId}` и использует только полученный ответ ЮKassa.

Сверка находит локальную запись по `metadata.donationId` и требует:

- `metadata.donationId` с локальным ID;
- суммы в копейках и валюты `RUB`;
- поддерживаемого типа и статуса платежа.

Если webhook пришел до сохранения provider ID, проверенный GET-платеж атомарно
привязывается к записи, у которой provider ID еще `null`. Уже сохраненный тот же
ID допустим. Другой уже привязанный ID является постоянным конфликтом: запись не
меняется, обработчик возвращает `200` и отправляет operational alert без
платежных идентификаторов, чтобы ЮKassa не повторяла неразрешимое событие 24 часа.
Поэтому ранний настоящий webhook не теряется, а create route позднее подтверждает
тот же ID.

До GET обработчик требует `type = "notification"`, поддерживаемое имя события и
строковый `object.id`. Ответ GET обязан иметь тот же `id`, который был запрошен,
`payment_method.type = "sbp"` и ожидаемую metadata.

IP allowlist ЮKassa может использоваться как дополнительный фильтр только там,
где reverse proxy гарантированно очищает и формирует адрес клиента. Доверять
пользовательскому `X-Forwarded-For` нельзя. Авторизованный GET остается
обязательной проверкой подлинности при любой инфраструктуре.

Webhook ограничивает `Content-Length` и фактический размер тела значением 64 KiB.
Некорректный JSON получает `400`, неизвестное корректно сформированное событие —
`200` без действий, временная ошибка ЮKassa или БД — `503` для повторной
доставки.
Секреты, тело webhook и идентификаторы платежа не записываются в журналы.

## Статусы, конкуренция и защита от дублей

Допустимы только переходы `PENDING → SUCCEEDED` и `PENDING → CANCELED`.
Терминальные статусы не меняются. Для `SUCCEEDED` заполняется `paidAt` временем
`captured_at` из проверенного ответа ЮKassa; для `CANCELED` поле остается пустым.

Репозиторий выполняет условное обновление с текущим статусом `PENDING`.
Одновременные return-запрос и webhook, повтор webhook и повторное создание
сводятся к одному изменению. После условного update выполняется чтение
актуальной записи. Уникальные индексы БД остаются последней линией защиты от
двух локальных записей с одним ключом или одним provider ID.

Матрица проверенного ответа ЮKassa:

- `pending` — локальный статус остается `PENDING`; result page показывает
  ожидание; после терминального webhook возвращается `503`, чтобы ЮKassa
  повторила уведомление после устранения временного расхождения;
- `succeeded` — требуются `paid = true` и корректный `captured_at`; выполняется
  условный переход в `SUCCEEDED`;
- `canceled` — выполняется условный переход в `CANCELED`;
- `waiting_for_capture` — недопустим при `capture = true`, БД не меняется,
  result page показывает техническое ожидание, webhook получает `503`;
- неизвестный статус, `succeeded` без `captured_at`, неверная сумма, валюта,
  metadata или тип платежа — protocol error без изменения БД.

Входное имя webhook-события не определяет переход. Если авторизованный GET уже
вернул терминальный статус, применяется этот статус даже при устаревшем имени
события. Если GET еще возвращает `pending` после терминального события, webhook
получает `503`. Для нового `pending`-ответа после create отсутствие
`confirmation_url` считается malformed provider response: provider ID
сохраняется, клиент получает `502`, а retry выполняет GET с тем же платежом.

Постоянные protocol errors — отсутствующий локальный donation, несовпадение
metadata, суммы, валюты, payment ID или `payment_method.type`, другой уже
привязанный provider ID и GET `404` — получают `200` без изменения БД и
operational alert с кодом причины, но без идентификаторов. Они не исправятся от
повторной доставки. Временные/неоднозначные состояния — GET `pending` после
терминального события, `waiting_for_capture`, malformed GET и ошибки сети/БД —
получают `503`.

## Ошибки и HTTP-контракт

- Тело create route ограничено 8 KiB, webhook — 64 KiB. Превышение дает `413`.
- Create route принимает только `application/json`; иначе `415`.
- Отсутствующий или чужой `Origin` получает `403` во всех окружениях.
- Невалидный JSON или поля получают `400` с безопасным кодом без stack trace.
- Непустой honeypot получает пустой `204`; БД и ЮKassa не вызываются.
- Выключенный feature gate и неверная server-конфигурация получают нейтральный
  `503`.
- Исчерпанный лимит получает `429` и целочисленный `Retry-After`.
- Конфликт UUID/provider ID и просроченная попытка получают `409`.
- Неизвестный donation ID на result page получает пользовательское error-state
  с HTTP `404`.
- HTTP-клиент ЮKassa использует timeout 5 секунд и `redirect: "error"`.
  Timeout, сеть, `429` и 5xx дают retryable `503` и сохраняют черновик.
  Provider `400` и прочие 4xx, кроме перечисленных отдельно, означают
  детерминированное отклонение: непривязанный черновик удаляется, create route
  возвращает `502 provider_rejected`. `401`/`403` удаляют непривязанный черновик
  и дают `503 configuration_unavailable`; `404` удаляет его и дает
  `502 provider_endpoint_error`. Malformed успешный ответ дает `502`, но черновик
  сохраняется из-за неопределенного исхода.
- Ошибка БД до вызова ЮKassa дает `503` и не вызывает провайдера. Ошибка БД после
  успешного ответа дает `503`, сохраняет доступную запись `PENDING` и требует
  retry с тем же UUID. Неизвестная ошибка route handler дает `500`; секреты и
  детали Prisma не попадают в ответ.
- Внешний confirmation URL берется только из ответа аутентифицированного запроса
  ЮKassa. Разрешен абсолютный HTTPS URL без username/password; входные данные
  пользователя никогда не задают redirect.
- DB rate limit использует HMAC-SHA256 нормализованного адреса клиента и
  отдельного секрета. В production включенный платежный контур требует
  `PAYMENTS_TRUST_PROXY=true`; доверенный reverse proxy обязан удалить входные
  forwarding headers и сформировать собственные. Бакеты удаляются после
  истечения TTL и не связываются с пожертвованиями.

## Переменные окружения

Используются только server-side значения:

- `YOOKASSA_SHOP_ID`;
- `YOOKASSA_SECRET_KEY`;
- `YOOKASSA_RETURN_URL`;
- `SITE_URL`.
- `PAYMENTS_ENABLED` с безопасным default `false`;
- `PAYMENTS_OFFER_VERSION`;
- `PAYMENTS_RATE_LIMIT_SECRET` длиной не менее 32 символов;
- `PAYMENTS_TRUST_PROXY`.

`YOOKASSA_RETURN_URL` обязан быть абсолютным URL локального result-маршрута.
Он имеет тот же origin, что `SITE_URL`, точный path `/donation/result` и не
содержит query, fragment или credentials; параметр donation добавляет сервер.
Production требует HTTPS и доверенный proxy при включенных платежах.
`NEXT_PUBLIC_*` для секретов запрещен. Тесты передают конфигурацию напрямую и не
зависят от локального `.env`.

`PAYMENTS_ENABLED=true` действительно включает маршрут только при опубликованном
юридическом источнике и точном совпадении `PAYMENTS_OFFER_VERSION`; форму и
create route обслуживает одна функция проверки gate, поэтому UI нельзя включить
отдельно от серверной защиты.

## Проверки

Разработка идет по циклу test-first. До реализации каждого поведения тест
должен падать по ожидаемой причине.

- unit-тесты суммы, UUID, оферты, денежных строк и конфигурации;
- контрактные тесты клиента ЮKassa с подмененным `fetch`: Basic Auth,
  `Idempotence-Key`, SBP JSON, timeout, malformed response, 4xx и 5xx;
- тесты репозитория: создание `PENDING`, повтор UUID, привязка provider ID,
  условные терминальные переходы и очистка однозначно отклоненного черновика;
- тесты оркестрации: повтор submit, 23/24-часовая граница, сбой до/после ответа
  ЮKassa, запрет автоматической замены stale UUID, lifecycle UUID в
  `sessionStorage`, ранний терминальный webhook до завершения create и
  несовпадение суммы;
- тесты webhook: malformed body, неизвестное событие, replay, несовпадающие
  metadata/сумма/валюта, webhook до привязки ID, полная status matrix,
  недоступность GET и конкурентная обработка;
- тесты create route: feature gate, origin, content type, размер тела, honeypot,
  все четыре DB rate limits, concurrent quota transaction, `429`, validation,
  точное отображение каждого provider 4xx и безопасные ответы ошибок;
- component-тесты формы: фиксированная и своя сумма, обязательная оферта,
  loading/error state и accessibility;
- тесты result page для `SUCCEEDED`, `CANCELED`, `PENDING`, неизвестной записи и
  временной ошибки сверки;
- обязательный PostgreSQL integration-тест уникальных ключей, гонки двух
  create-вставок, ранней привязки webhook, rate-limit buckets и конкурентного
  условного перехода с защитой имени тестовой базы;
- регрессия существующей публичной страницы и admin-списка пожертвований;
- полный `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`,
  `npm run db:validate`, `npm run db:generate`, `npm audit --audit-level=high`
  и `git diff --check`.

В `package.json` добавляется `test:integration:payments`. Команда требует
`PAYMENTS_TEST_DATABASE_URL`, разрешает только явно тестовое имя базы и завершается
ошибкой, а не skip, если база не задана или недоступна. Отдельный обязательный
CI job поднимает PostgreSQL, применяет миграции и запускает эту команду. Обычный
`npm test` остается быстрым и не маскирует интеграционные тесты как пройденные.

После получения тестовых реквизитов отдельно проверяются реальный переход на
страницу ЮKassa, отображение динамического QR, возврат на сайт, доставка обоих
webhook-событий и совпадение статуса в ЮKassa, БД и админке.

## Критерии готовности

- Анонимный пользователь может создать только валидное разовое пожертвование и
  перейти к СБП без передачи персональных данных.
- Один UUID не создает два платежа ни локально, ни в ЮKassa.
- Просроченный непривязанный UUID не отправляется в ЮKassa повторно после окна
  идемпотентности и не заменяется без явного подтверждения пользователя.
- Локальный успешный статус появляется только после авторизованной проверки
  платежа у ЮKassa.
- Повторы и конкурирующие обработчики не меняют терминальный статус и не
  дублируют запись.
- Страницы результата понятны, доступны, не индексируются и не раскрывают
  технические данные.
- Все автоматические проверки проходят без реальных секретов.
- Платежи невозможно включить без явного feature gate, production HTTPS,
  доверенного proxy и опубликованной проверенной оферты.
- Обязательная PostgreSQL integration-команда выполнена, а не пропущена.
- Ограничение приемки без тестовых реквизитов явно отражено в отчете.
