# Оптимизация webFond: выбранные решения

Дата: 19 октября 2026 года. Статус: предложение для реализации; код приложения этим документом не изменяется.

## Цель и исходное состояние

Уменьшить объём чтения из PostgreSQL и размер изображений, восстановить полноценный CI и обеспечить независимую очистку технических данных. Сохранить платежные гарантии, статусы публикации, optimistic concurrency, атомарный audit и текущую структуру публичных страниц.

Повторный локальный прогон при подготовке документа: 1458 тестов прошли, 12 пропущены; typecheck завершился с кодом 0. Предыдущие девять падений больше не считаются актуальными. В рабочем дереве остаются изменения публичного сайта; их нельзя перезаписывать или незаметно включать в коммиты оптимизации. Интеграции с PostgreSQL и настройки production этим прогоном не проверены.

## Варианты и выбор

| Вариант | Польза | Цена и риск | Решение |
| --- | --- | --- | --- |
| Точечная оптимизация запросов, CI, обслуживания и загрузки изображений | Устраняет подтверждённую лишнюю работу, легко сравнить до/после | Несколько небольших независимо выпускаемых изменений | Выбран для первого релиза |
| Сразу добавить общий межзапросный кеш | Может снизить чтение при большом повторном трафике | Новая инфраструктура, инвалидация, согласованность экземпляров, ограничения Timeweb | Только после измерений и выполнения отдельного условия ниже |
| Переписать CMS/сервер или перейти на другой хостинг | Потенциал существенной перестройки | Высокая стоимость, регрессии платежей, нет доказанной необходимости | Исключён |

Отсутствие межзапросного кеша само по себе не ошибка. В первом релизе сохраняются динамические страницы и React.cache для дедупликации внутри запроса. Не включать Cache Components и не удалять force-dynamic массово: это отдельная миграция поведения.

## Контракты первого релиза

1. Главная получает максимум три опубликованных документа и три проекта непосредственно из БД. Порядок прежний: publishedAt DESC, id DESC. Пожертвования агрегируются только для выбранных проектов с положительной целью. Пустой список и ошибка загрузки остаются разными состояниями.
2. Существующие экспортируемые функции и их параметры client сохраняют совместимость. Для главной вводятся отдельные ограниченные загрузчики. Полные коллекции не обрезаются скрыто, пагинация публичных разделов не добавляется в этот релиз.
3. Ссылки последних десяти audit-событий разрешаются пакетно: максимум один запрос на присутствующий тип сущности, уникальные ID, без чтения персональных данных. Всё чтение остаётся внутри прежней RepeatableRead-транзакции.
4. Очистка PaymentRateLimitBucket запускается независимо от PAYMENTS_ENABLED. Удаляются только expiresAt <= серверного cutoff, ограниченными SQL-пакетами; повтор и параллельный запуск безопасны. Старое удаление из платежного запроса снимается только после подтверждения работающего scheduler.
5. Новые редакционные изображения JPEG/PNG/WebP преобразуются в ограниченный WebP в памяти и сохраняются через существующее хранилище. POST загрузки сохраняет ответ {url}; fileUrl PDF, банковские QR и старые imageUrl остаются рабочими. Внешние URL не скачиваются сервером. Новая схема БД и изменение публичных URL старых файлов не требуются.
6. CI использует временную локальную тестовую БД и явные DATABASE_URL и DATABASE_URL_UNPOOLED. Все DB-suite действительно выполняются; skip не считается DB-проверкой. Обычные проверки не отменяют обязательные платежные интеграции.
7. Production audit должен оставаться без high/critical. У dev-зависимостей сначала искать совместимое исправление; если его нет, зафиксировать точный advisory, ограничение воздействия, владельца и повторную проверку через 14 дней. Не откатывать Next/ESLint на несовместимый major ради зелёного audit.

## Кеш: условие следующего этапа

После первого релиза измерить тестовый контур на одинаковых данных и ресурсах: минимум 100 запросов на маршрут, concurrency 1 и 5, после прогрева. Первоначальная цель: p95 TTFB публичных страниц <= 500 мс; это проектная цель, а не обещание результата или универсальная норма.

Рассматривать общий кеш только если после оптимизации p95 остаётся выше цели, повторные DB-чтения дают не менее половины серверного времени и представительная проверка показывает, что кеш позволяет достичь цели или снизить p95 хотя бы на 20%. Исключить сетевую задержку до БД, нехватку ресурсов и медленные планы запросов как первопричину.

При выполнении условия выбран общий Redis в допустимой российской инфраструктуре, рядом с приложением, и совместимый с установленной Next.js cache handler. Нельзя заменять его глобальным Map или дисковым кешем контейнера. Перед реализацией отдельным проектированием фиксируются версия handler API, TTL, инвалидация со всех экземпляров, раздельные сроки свежести текстов/сборов, поведение при сбое Redis и совместимость релизов. Платежные решения, админка, контакты, согласия и реквизиты в общий кеш не попадают. Это условный отдельный релиз, а не обязательная зависимость исправлений первого релиза.

## Проверка результата и границы

- Сравнить число SQL-запросов, число возвращённых строк, p50/p95, ошибки и память до/после на одной тестовой БД.
- В первом релизе нет миграций схемы; существующие индексы сначала проверить EXPLAIN на тестовых данных.
- Каждый этап отдельным коммитом после проверки; production выпускать по частям.
- Readiness конфигурации не является проверкой PostgreSQL. Проверять БД отдельно.
- Не публиковать и не отправлять реальные обращения/пожертвования, не менять production-переменные при подготовке плана.
