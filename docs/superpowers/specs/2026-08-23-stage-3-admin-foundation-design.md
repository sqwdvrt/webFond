# Этап 3. Основа данных и защищенная админка

## Цель

Подготовить первый рабочий срез этапа 3: зафиксировать существующую Prisma-схему
начальной миграцией и добавить защищенный вход в `/admin` для одной учетной
записи. Управление контентом, просмотр пожертвований и CSV-экспорт остаются для
следующих срезов этапа 3.

## Принятые решения

- Вход выполняется по логину и паролю одной учетной записи.
- Локальные значения: логин `admin`, пароль `admin12345`. Это известные
  development-данные, которые обязательно заменяются при развертывании.
- Логин, пароль и секрет подписи сессии читаются только на сервере из
  `ADMIN_USERNAME`, `ADMIN_PASSWORD` и `AUTH_SECRET` в `.env`.
- Реальные значения не попадают в git. В `.env.example` остаются безопасные
  примеры и пояснения.
- Таблица администраторов не создается. Модель `AdminUser` удаляется из Prisma,
  потому что она не нужна выбранному сценарию.
- Auth.js не подключается: для одной учетной записи достаточно небольшого
  локального модуля с подписанной сессией.

## Объем работ

### Prisma

Существующая схема PostgreSQL сохраняет модели:

- `Project` для управляемых проектов;
- `NewsPost` для новостей;
- `Document` для отчетов и других опубликованных файлов;
- `SiteSetting` для реквизитов и других единичных настроек;
- `Donation` для будущего платежного контура и списка пожертвований;
- `ContactRequest` для будущей серверной формы обращений.

Перечисления статусов и индексы остаются в схеме. Начальная SQL-миграция должна
полностью воспроизводить схему без обращения к рабочей базе во время генерации.
После изменения обязательны `prisma validate` и `prisma generate`. SQL также
сравнивается с актуальной схемой через `prisma migrate diff`; если доступна
одноразовая PostgreSQL-база, миграция дополнительно применяется к ней с нуля.

### Авторизация

Публичный маршрут `/admin/login` показывает компактную форму с полями «Логин» и
«Пароль». Успешный вход создает подписанную сервером сессию и переводит
пользователя на `/admin`. Неверные данные возвращают одинаковое нейтральное
сообщение без указания, какое поле ошибочно.

Маршрут `/admin` содержит минимальный экран администратора с названием фонда,
именем текущей учетной записи и действием выхода. Это подтверждает, что защита
работает, но не имитирует еще не реализованное управление контентом.

Неавторизованный запрос к `/admin` и вложенным страницам перенаправляется на
`/admin/login`. Уже авторизованный пользователь при переходе на страницу входа
перенаправляется в `/admin`. Выход удаляет cookie и возвращает на страницу входа.

## Сессия и безопасность

- Cookie содержит версию формата, логин, время выпуска и время истечения.
- Payload подписывается HMAC-SHA-256 с `AUTH_SECRET`; неподписанные и измененные
  значения отклоняются.
- Срок сессии составляет 8 часов.
- Cookie имеет атрибуты `HttpOnly`, `SameSite=Lax`, `Path=/` и `Secure` в
  production.
- Сравнение логина, пароля и подписи выполняется без раннего выхода по значению,
  чтобы не создавать простой timing side channel.
- `AUTH_SECRET` обязателен и должен содержать не менее 32 символов. Сервер не
  стартует с рабочей авторизацией при неполной конфигурации.
- Ошибки авторизации не содержат пароль и не записывают его в журнал.

Ограничение частоты хранит в памяти процесса только счетчики неудачных попыток,
необратимый отпечаток адреса клиента и время блокировки. На production адрес
берется из первого значения `x-forwarded-for` только за доверенным reverse
proxy, затем из `x-real-ip`; отсутствие обоих значений образует общий ключ
`unknown`. На локальном сервере используется отдельный ключ `local`. Перед
сохранением значение подписывается HMAC с `AUTH_SECRET`, поэтому исходный адрес
не остается в памяти. После пяти ошибок за 15 минут вход для этого адреса
блокируется на 15 минут. Хранилище имеет ограниченный размер и очищает
устаревшие записи. Это защита первого среза для одного процесса; перед
горизонтальным масштабированием ее нужно заменить общим хранилищем.

## Архитектура

- Модуль конфигурации проверяет серверные переменные окружения при первом
  обращении к авторизации и не импортируется клиентскими компонентами. Сборка
  публичного сайта не требует admin-секретов; тесты передают конфигурацию явно.
- Модуль сессии отвечает только за создание, проверку и удаление cookie.
- Модуль проверки учетных данных отвечает за сравнение значений и rate limiting.
- Серверные действия формы связывают эти модули с перенаправлениями и возвращают
  форме только безопасные состояния ошибки.
- Layout route group `/admin/(protected)` проверяет сессию на сервере до
  отрисовки защищенного содержимого. `/admin/login` находится вне этой группы,
  поэтому перенаправления не образуют цикл.
- Защита будущих изменяющих данные действий должна повторно проверять сессию;
  один layout не считается достаточной авторизацией серверной операции.

## Ошибки и состояния

- Пустые поля дают локальную ошибку валидации и не создают сессию.
- Неверный логин или пароль дают одно сообщение: «Неверный логин или пароль».
- При временной блокировке форма сообщает, что вход временно недоступен, без
  раскрытия счетчиков или адреса клиента.
- Поврежденная, просроченная или подписанная другим секретом cookie считается
  отсутствующей и удаляется при следующем ответе, где это возможно.
- Отсутствующая серверная конфигурация дает контролируемую ошибку конфигурации,
  не раскрывающую значения переменных.

## Доступность и интерфейс

- У каждого поля есть видимая связанная подпись и корректный `autocomplete`.
- Ошибка связана с формой через `aria-live` и не меняет размеры элементов
  управления.
- Форма полностью работает с клавиатуры; focus-состояния соответствуют
  существующей визуальной системе.
- В административной части используется существующая палитра и типографика без
  копирования публичного маркетингового layout.
- Страница входа и все маршруты `/admin` закрыты от индексации.

## Проверка

Тесты создаются до производственного кода и покрывают:

- чтение и проверку серверной конфигурации;
- успешную и неуспешную проверку учетных данных;
- блокировку после пяти неудачных попыток и снятие блокировки по времени;
- создание, проверку, истечение и подделку сессии;
- перенаправление гостя с `/admin` на `/admin/login`;
- перенаправление действующей сессии со страницы входа в `/admin`;
- успешный вход, нейтральную ошибку и выход;
- отсутствие `AdminUser` и наличие требуемых моделей в Prisma-схеме.

Финальная проверка: `npm test`, `npm run lint`, `npm run typecheck`,
`npm run db:validate`, `npm run db:generate`, `npm run build` и
`git diff --check`. В браузере проверяются вход, выход, неверный пароль,
клавиатурная навигация и мобильный экран 390 x 844.

## Вне этого среза

- создание нескольких администраторов и роли `ADMIN`/`EDITOR`;
- восстановление и смена пароля, одноразовые коды и двухфакторная авторизация;
- редактирование проектов, новостей, документов и реквизитов;
- загрузка файлов и изображений;
- список пожертвований, фильтры и CSV-экспорт;
- ЮKassa, СБП, webhook и рабочая форма пожертвования;
- распределенное хранилище rate limiting.
