# Мобильное приложение: решения этапа 0

Дата проверки: 13 сентября 2026. Ветка: `codex/mobile-stage-0`, исходная ревизия `b0c90f5`.

## Продукт

Пять вкладок: Сборы, Отчет, Проекты, Новости, Профиль. Сборы — проекты с целью и прогрессом. Контент и пожертвования доступны гостю; вход по коду на почту необязателен. В профиле: сохраненные сборы, почта, удаление аккаунта. История платежей и push не входят. Фонд работает в России; аккаунтов магазинов пока нет; ЮKassa настроена на сайте со слов владельца.

## Технология

Выбран React + Vite + Capacitor с упакованными локальными web-ресурсами; Next.js и PostgreSQL остаются сервером. Решение предварительно подтверждено web-сборкой и генерацией платформ, но еще не нативным запуском. Отсутствие SDK не является доказательством несовместимости Capacitor и поводом переписывать на Expo.

- `mobile/` — самостоятельный npm-пакет и lockfile. Корневые TypeScript, ESLint и Vitest исключают его. Изменения не требуют новых production-переменных сайта.
- Установлены Capacitor 8.5.2, React 19.3.0, Vite 8.3.0, App Launcher 8.0.1. Конкретные зависимости закреплены в `mobile/package-lock.json`.
- Нет `server.url`: в Android/iOS копируется `dist/`. В сборке нет ключей БД, ЮKassa или почты.
- Предварительный идентификатор `ru.fondbitdobru.mobile`. Не зарегистрирован в магазинах; подтвердить владельцем до первой загрузки подписанной сборки.
- Сгенерированные проекты: iOS deployment target 15.0; Android minSdk 24, compileSdk/targetSdk 36. Это технический минимум шаблона, не подтвержденная матрица устройств или гарантия требований магазинов к моменту выпуска.
- Node установлен 25.4.0; для воспроизводимой дальнейшей работы предпочтителен поддерживаемый LTS, подходящий выбранным инструментам. Этап 0 проверен на установленной версии.
- iOS использует Swift Package Manager; CocoaPods сейчас не нужен.

## Сессии

На этапе 0 авторизации и хранения токенов нет. План для этапа 4: короткоживущий access token в памяти; refresh token в iOS Keychain / Android Keystore через поддерживаемый плагин. Кандидат — `@aparajita/capacitor-secure-storage` 8.0.0, заявляющий поддержку Capacitor 8; его нативная сборка еще не проверена. iCloud-синхронизацию токенов отключить. Отзыв сессий на сервере обязателен; учесть сохранение Keychain после переустановки и удаление данных после выхода.

Web-реализация этого плагина хранит данные незашифрованно в localStorage: ее нельзя использовать для production-токенов. Для web-профиля отдельно выбрать защищенную cookie-сессию либо оставить авторизацию только в нативном клиенте до безопасной реализации. [Документация плагина](https://github.com/aparajita/capacitor-secure-storage).

## Платежи

В коде сайта есть redirect-подтверждение ЮKassa, return_url и привязка пожертвования к проекту. Выбран путь: приложение открывает страницу помощи сайта во внешнем системном браузере, сайт создает платеж. Нового платежного SDK и передачи ключей в клиент не требуется для этого сценария. Допустимость использования текущего магазина ЮKassa и договора в выбранном сценарии подтвердить перед живыми тестами.

Для iOS базовый вариант соответствует описанному Apple внешнему сбору средств; прямой сбор внутри приложения для одобренных НКО имеет дополнительные условия. Google отдельно оговаривает tax-exempt donations; статус конкретных пожертвований не предполагать без документов фонда. [Apple 3.2.1/3.2.2](https://developer.apple.com/app-store/review/guidelines/), [Google Payments](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en), [redirect-сценарий ЮKassa](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/smart-payment).

В проверочном клиенте App Launcher получает только две фиксированные HTTPS-ссылки: главная сайта и тестовый PDF W3C. Он не создает платеж и не принимает URL от пользователя. Проверить реальное открытие Safari/браузера, банка и возврат после выгрузки приложения предстоит на устройствах. Browser-тест подменяет window.open и проверяет адреса, но не доказывает работу нативного App Launcher. Для платежного возврата позднее потребуется отдельное решение по app/universal links и серверному статусу.

## Почта

Наличие доменной почты фонда пока неизвестно. В России есть SMTP-вариант Яндекс 360 для бизнеса; наличие документации не означает выбранный тариф или разрешение массовой транзакционной отправки. Перед этапом 4 проверить ограничения отправителя, домен, SPF/DKIM/DMARC, лимиты и доставляемость; при необходимости выбрать специализированный транзакционный сервис. [Настройки SMTP Яндекс](https://yandex.ru/support/yandex-360/business/mail/ru/mail-clients/others). Почтовый провайдер не подключался, писем не отправлено.

## Найденные технические риски

1. Существующий серверный lockfile: `npm audit --omit=dev` сообщает critical для Next.js 16.3.1 и high для sharp. До production требуется отдельная проверка применимости и обновление. Это сведения npm audit, не доказательство эксплуатации или уязвимости боевого развертывания. [Next AVIF](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4), [Next Windows](https://github.com/advisories/GHSA-p293-qw3h-jr36), [sharp](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c).
2. Мобильный npm audit: 0 production-уязвимостей, 3 moderate в цепочке сборщика `@capacitor/cli -> xcode -> uuid`. Не применялся `audit fix --force`; риск инструментов сборки остается открытым до обновления/проверки upstream. [uuid advisory](https://github.com/advisories/GHSA-w5hq-g745-h8pq).
3. Серверный lint: существующая ошибка `react-hooks/set-state-in-effect` в `src/app/admin/(protected)/media-url-field.tsx:40` и warning img в `bank-qr-transfer.tsx:39`. Эти файлы не изменялись этапом 0.
4. Нативные клавиатура, PDF, возврат и защищенное хранилище не проверены без инструментов/устройств. Доступность сайта и реальных платежей на production этим этапом не подтверждается.
